# QR Browser Data Transport Library 仕様書 v1

## 1. 概要

Webブラウザ間で、カメラを用いてQRコードを連続的に読み取ることでデータ通信を行うライブラリ。

送信側ブラウザがQRコードを高速に切り替えて表示し、受信側ブラウザがカメラで連続的に撮影・解析することで、単一のQRコードでは収まらないデータを複数QRに分割して転送する。

実装言語は以下を使用する。

- TypeScript
- Rust / WebAssembly

本ライブラリは、単純なQRコード生成・読み取りだけでなく、複数のQRコードを用いたデータ転送プロトコルを提供する。

---

## 2. 基本方針

### 2.1 通信方向

通信そのものは一方向とする。

```text
Browser A
   │
   │ QR表示
   ▼
┌─────────┐
│   QR    │
└─────────┘
   │
   │ Camera
   ▼
Browser B
```

ただし、ライブラリ自体は送信・受信の双方に対応する。

そのため、同一ライブラリを以下のように利用できる。

- Browser A: Sender
- Browser B: Receiver

将来的な双方向通信を妨げない構造とする。

## 3. データ処理の基本構造

内部の標準データ形式は `Uint8Array` とする。

```text
Input
  ↓
Data Format Conversion
  ↓
Uint8Array
  ↓
Protocol Encoding
  ↓
QR Encoding
  ↓
QR Display
  ↓
Camera
  ↓
QR Detection / Decoding
  ↓
Protocol Decoding
  ↓
Uint8Array
  ↓
Data Format Conversion
  ↓
Output
```

---

## 4. API構成

公開APIは2層構成とする。

### 4.1 Core API

低レイヤーAPI。

通信データの基本形式を `Uint8Array` に限定する。

Core APIでは以下を担当する。

- データ分割
- フレーム生成
- フレーム番号管理
- QR単位のデータ生成
- フレームchecksum
- 全体checksum
- フレーム再構成
- checksum検証
- 通信終了判定

Core APIは、ブラウザのカメラやCanvas等の環境に依存しない構造とする。

概念例：

```ts
Encoder
Decoder
```

---

### 4.2 High-level API

一般利用者向けAPI。

入力として複数のデータ形式を受け付け、内部で `Uint8Array` に変換する。

例：

```ts
const transport = new QRTransport(options);

await transport.send(data);
```

High-level APIでは、以下を担当する。

- 入力データ形式の変換
- データフォーマット識別情報の付与
- カメラ制御
- QR表示
- QR読み取り
- Worker制御
- Runtime選択
- Core APIとの接続

---

## 5. 入力データ形式

内部形式は `Uint8Array` とするが、High-level APIでは複数の入力形式を使用できるようにする。

具体的な対応形式は今後決定する。

候補：

- `Uint8Array`
- `ArrayBuffer`
- `string`
- JSON
- `Blob`
- その他

通信データには、元データのフォーマットを識別するためのモード情報を含める。

```text
[Data Format Mode]
[Data Payload]
```

これにより、受信側で元のデータ形式を判別・復元できる構造とする。

---

## 6. QR通信プロトコル

1つのQRコードを1フレームとして扱う。

大きなデータは複数のQRフレームへ分割する。

```text
Data
 │
 ├── QR Frame 0
 ├── QR Frame 1
 ├── QR Frame 2
 ├── ...
 └── QR Frame N
```

各QRフレームには通信に必要な制御情報を含める。

現時点で想定する情報：

- Protocol Version
- Session / Transfer ID
- Frame Number
- Total Frame Count または終了情報
- Data Format Mode
- Payload
- Frame Checksum
- 終端情報

具体的なバイト配置、ビット幅、エンコード方式はv1では未決定とする。

---

## 7. Checksum

checksumは2段階で使用する。

### 7.1 フレームchecksum

各QRフレーム内にchecksumを含める。

```text
QR Frame
┌────────────────────┐
│ Header             │
│ Frame Information  │
│ Payload            │
│ Frame Checksum     │
└────────────────────┘
```

受信側はQR単位でchecksumを検証し、破損したフレームを検出する。

checksumアルゴリズムは未決定。

---

### 7.2 全体checksum

通信データ全体についてchecksumを生成する。

最終QRフレームに全体checksumを含める。

```text
Frame 0
Frame 1
Frame 2
...
Frame N
  └─ Final QR
       └─ Overall Checksum
```

受信側は全フレームを再構成した後、全体checksumを検証する。

これにより、

- フレーム単位の破損
- フレーム欠落
- フレーム順序異常
- 再構成後のデータ不整合

などを検出できるようにする。

具体的なchecksumアルゴリズムは未決定。

---

## 8. フレーム番号

各QRフレームにはフレーム番号を含める。

例：

```text
Frame 0
Frame 1
Frame 2
Frame 3
...
```

これにより、受信側で以下を検出可能にする。

- 順序
- 欠落
- 重複
- 再送されたフレーム
- 不正なフレーム

具体的なフレーム番号のサイズは未決定。

---

## 9. 通信速度

QRの切り替え速度は固定値としない。

利用者が設定によって変更できる構造とする。

設定対象の候補：

- QR表示FPS
- QR切り替え間隔
- 同一QRの表示回数
- QRサイズ
- QR Version
- Error Correction Level
- カメラ設定
- 解析頻度
- Worker使用
- その他パフォーマンス関連設定

具体的な設定項目・デフォルト値は未決定。

## 10. QRサイズ

QRサイズも設定可能とする。

QR VersionやError Correction Level等、QRコードの容量・認識率に影響する設定を利用者が指定できる構造とする。

```ts
new QRTransport({
    qr: {
        // QR関連設定
    }
});
```

具体的なAPIおよび設定項目は未決定。

## 11. Worker / OffscreenCanvas

可能な環境ではWorkerおよびOffscreenCanvasを利用する。

ただし、以下の場合はMain Thread上で処理する。

- Workerが使用できない
- OffscreenCanvasが使用できない
- 利用者が設定でWorker使用を無効化している
- その他、実行環境上の理由でWorkerを使用できない

概念構造：

```text
Worker使用時

Main Thread
    │
    └── Worker
          │
          ├── OffscreenCanvas
          ├── Image Processing
          └── QR Processing
```

Workerを使用しない場合：

```text
Main Thread
    │
    ├── Canvas
    ├── Image Processing
    └── QR Processing
```

---

## 12. Main / Worker間の共通化

Worker使用時と非使用時で同じ処理を二重実装しない。

共通処理をRuntime Wrapper等の抽象化層を介して利用する。

```text
                  Common Processing
                         │
                  Runtime Wrapper
                    /          \
                   /            \
          Main Runtime      Worker Runtime
               │                  │
               ▼                  ▼
          Main Thread          Worker
```

WorkerとMain Threadで異なるのは、主に実行環境との接続部分とする。

QR解析、プロトコル処理等の共通ロジックは可能な限り共有する。

---

## 13. Workerの提供方式

利用者が別途Worker用ファイルを指定する必要がない構成を目標とする。

同一JavaScriptファイル内で、自身をWorkerとして起動できる構造とする。

概念：

```ts
if (isWorkerContext()) {
    runWorker();
} else {
    runMain();
}
```

具体的なWorker生成方法は未決定。

候補：

- Module Worker
- Blob Worker
- その他

CSP、ESM、CDN等の環境への対応については実装時に検討する。

---

## 14. Rust / WebAssembly

Rust / WASMは、高負荷な画像処理・QR解析等への利用を想定する。

ただし、Rust/WASMへどこまで処理を移すかは現時点では未決定。

以下について調査・実測した上で決定する。

- 画像解析
- QR検出
- QRデコード
- SIMD
- WebAssemblyの性能
- WASMへの画像データ転送コスト
- Canvas / OffscreenCanvasとの連携
- Workerとの組み合わせ
- メモリコピーのコスト

Rust/WASMの担当範囲は、性能調査の結果をもとに決定する。

## 17. v1での設計上の原則

1. 内部データ形式は `Uint8Array` を基本とする。
2. High-level APIでは複数の入力形式を受け付ける。
3. 通信データ自身にデータフォーマット情報を含める。
4. QR 1枚を1フレームとして扱う。
5. 各フレームにフレーム番号を含める。
6. 各フレームにchecksumを含める。
7. 最終QRに通信全体のchecksumを含める。
8. QR速度・サイズ等は可能な限り設定可能にする。
9. Worker / OffscreenCanvasが使用可能なら利用できる構造にする。
10. Workerが利用できない場合はMain Threadへフォールバックする。
11. Worker使用時と非使用時で処理ロジックを二重実装しない。
12. 共通処理とRuntime固有処理を分離する。
13. Core APIとHigh-level APIを分離する。
14. Rust/WASMの担当範囲は性能調査後に決定する。
15. 将来的な双方向通信への拡張を妨げない設計とする。
