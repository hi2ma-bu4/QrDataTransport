# QrDataTransport 仕様書 v6

## 1. 概要

QrDataTransport は、ブラウザ間で QR コードを高速に切り替え表示・撮影することでデータ通信を行うためのライブラリである。

実際の物理通信は QR コードを介した**一方向通信**である。

ただしライブラリとしては、

* 送信機能
* 受信機能

の双方を提供する。

内部で扱う基本データ型は `Uint8Array` とする。

---

# 2. API構成

APIは以下の3層に分離する。

```text
┌──────────────────────────────────────────────────────┐
│                  QrDataTransport                     │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │

│  │ Camera / DOM / Canvas / Worker                 │  │
│  │ MediaStream / OffscreenCanvas / Timing         │  │
│  └──────────────────────┬─────────────────────────┘  │
│                         │                            │
│  ┌──────────────────────▼─────────────────────────┐  │
│  │                Transport API                   │  │
│  │ Send / Receive / Timing / State / Error        │  │
│  └──────────────────────┬─────────────────────────┘  │
│                         │                            │
│  ┌──────────────────────▼─────────────────────────┐  │
│  │                  Data API                      │  │
│  │ Uint8Array / Protocol / Frame / QR Data        │  │

└──────────────────────────────────────────────────────┘
```

## 2.1 Data API

通信データおよび QR プロトコルそのものを扱う。

ブラウザに依存しない。

主な責務：

* `Uint8Array` の処理
* String / `Uint8Array` のデータ変換
* データ種別の管理
* データの分割
* Frame生成
* QR用ビットデータ生成
* QRデータの解析
* Frameの再構築
* Frame CRC検証
* Overall CRC検証
* QRデコード後データの処理
* Rust / WASMによる処理

Data APIは実際のカメラ、DOM、Canvas等を直接操作しない。

---

## 2.2 Transport API

通信そのものを管理する。

主な責務：

* Send開始
* Send停止
* Receive開始
* Receive停止
* Frame順序管理
* 送信状態管理
* 受信状態管理
* QR切替タイミング管理
* Data APIとBrowser Runtime APIの橋渡し
* 通信エラー管理
* 通信完了管理

---

## 2.3 Browser Runtime API

実際のブラウザ機能を扱う。

主な対象：

* Camera
* MediaStream
* DOM
* Canvas
* OffscreenCanvas
* Worker
* Timing

Browser Runtime APIは、Data APIが生成した QR のモジュール情報を実際に表示する。

また受信時には、Cameraから取得した画像をData API側へ渡す。

# 3. 基本データ形式

内部の基本データ形式は `Uint8Array` とする。

文字列を扱う場合は UTF-8 として扱う。

Data APIから通信結果を返却する際は、データ本体だけではなくデータ型情報も返却する。

```ts
{
    type: "Uint8Array" | "string",
    data: Uint8Array | string
}
```

これにより、Transport API等が返却されたデータの型を推測する必要はない。

Stringとして扱う場合でも、QR Payloadの生成・分割・CRC検証・再構築等の内部処理では、Payloadを基本的に `Uint8Array` / bitstreamとして扱う。

---

# 4. QR通信方式

通信対象データを複数の QR に分割する。

QRは必ず以下の順番で構成される。

```text
0 → 1 → ... → N-1
```

ただし送信側は受信側の状態を知ることができないため、1回送信しただけでは停止しない。

送信中は以下のように無限ループする。

```text
0 → 1 → ... → N-1 → 0 → 1 → ... → N-1 → ...
```

送信を停止するのはユーザー/APIによる `stop` 操作のみとする。

送信側は、全Frameを一度送信したことを理由に自動停止しない。

Frame Numberは0-basedであり、通信上の最初のFrameを `0` とする。

---

# 5. QRの種類

QRには以下の3種類の構造が存在する。

* First QR
* Intermediate QR
* Final QR

ただし、QRごとに完全に別の構造を持たせるのではなく、基本的なフィールドを順番に配置する。

## First QR

```text
[Start Bit]
[Library Format Version]
[Total QR Count]
[Frame Number]
[Data Type]
[Payload Length]
[Payload]
[Padding]
[Frame Checksum]
```

## Intermediate QR

```text
[Start Bit]
[Frame Number]
[Payload Length]
[Payload]
[Padding]
[Frame Checksum]
```

## Final QR

```text
[Start Bit]
[Frame Number]
[Payload Length]
[Payload]
[Padding]
[Frame Checksum]
[Overall Checksum]
```

---

# 6. First / Intermediate / Final の判定

## 6.1 First QR

`Start Bit = 1` の QR が First QR である。

First QRには通信全体を解析するために必要な情報が含まれる。

First QRのFrame Numberは必ず `0` である。

---

## 6.2 Intermediate / Final

First QRを受信して通信情報が確立された後は、Frame Numberによって判定する。

```text
Frame Number < Total QR Count - 1
    → Intermediate

Frame Number = Total QR Count - 1
    → Final
```

したがって、Final QRには特別な専用識別bitを追加しない。

Frame Numberは0-basedであるため、Total QR Countを `N` とした場合の有効Frame Numberは、

```text
0 ～ N-1
```

となる。

---

## 6.3 Total QR Count = 1

`Total QR Count = 1` の場合、

```text
Frame Number = 0
Total QR Count = 1
```

となるため、そのQRは、

* First
* Final

の両方に該当する。

構造は既存のフィールド順を崩さず、必要なフィールドを順番に配置することで整合性を取る。

実装上はQRを読みながら条件に応じて必要なフィールドを処理することで、通常の複数Frame通信と `Total QR Count = 1` の両方を扱える。

---

# 7. ビットストリーム

すべてのフィールドは、1つの連続したビットストリームとして扱う。

フィールド境界でbyte alignmentを行わない。

例えば、

```text
[4bit][16bit][3bit][...]
```

のようにフィールドが連続する場合、次のフィールドは前のフィールドの直後から開始する。

フィールドの開始位置がbyte境界に一致するとは限らない。

---

# 8. ビット順

ビットストリーム上の通常の固定長フィールドは **MSB-first** とする。

つまり数値を指定bit数で表現する場合、上位bitから順番にビットストリームへ配置する。

例：

```text
8bit value = 0x96

0x96
= 10010110
```

ビットストリーム上では、

```text
1 0 0 1 0 1 1 0
```

の順番で配置する。

---

# 9. Uint8Array のbyte / bit順

`Uint8Array` のPayloadは、

* byte順：`Uint8Array` のindex順
* 各byte内部のbit順：MSB-first

とする。

例えば、

```ts
new Uint8Array([
    0x96,
    0x2A,
    0xF0
])
```

は、

```text
10010110 00101010 11110000
```

の順番でビットストリームへ配置する。

String modeにおいても、最終的なPayload検証・CRC処理ではPayloadを `Uint8Array` / byte列として扱う。

---

# 10. Varint

`Payload Length` は可変長整数として格納する。

1グループは7bitで構成される。

```text
[Continuation Bit][6bit Data]
```

* Continuation Bit = `1`

  * 後続グループが存在する
* Continuation Bit = `0`

  * このグループが最後

---

## 10.1 Varint内部のbit順

通常のビットストリームはMSB-firstだが、**Varint内部の6bit DataのみLSB-first**とする。

つまり、

```text
通常フィールド
→ MSB-first

Varintの6bit Data
→ LSB-first
```

という例外的な構造になる。

このLSB-firstはVarintの内部表現にのみ適用され、Varintフィールド全体をMSB-first/LSB-firstに反転するものではない。

---

## 10.2 6bit Data

各グループの6bit Dataには、値の下位6bitから格納する。

次のグループには、その次の6bitを格納する。

これはLEB128に類似した方式である。

---

## 10.3 最小表現

Payload Lengthは最小bit数で表現する。

冗長な表現は禁止する。

例えば0は、

```text
[Continuation=0][Data=000000]
```

の7bitで表現する。

---

## 10.4 64の例

64の場合、

```text
64 = 0b1000000
```

なので、

```text
[1][000000][0][000001]
```

となり、合計14bitとなる。

---

# 11. Start Bit

Start Bitは1bit。

```text
First QR:
1

First QR以外:
0
```

Start Bitは通信開始を識別するために使用する。

First QRが読み込まれていない状態では、後続QRについて通信を正式には開始しない。

---

# 12. Library Format Version

4bit。

現在の仕様では、

```text
0b0001
```

から開始する。

```text
0b0000
```

は未使用。

Version 0は無効なQRとして扱う。

ライブラリが対応していない将来Versionについては、可能な範囲で構造を解析する。

ただし、現在のライブラリが理解できない構造である場合は通信エラーとする。

---

# 13. Total QR Count

First QRのみ存在する。

16bit。

有効範囲：

```text
1 ～ 65535
```

`0` は無効。

Total QR Countは通信全体のQR数を表す。

この値からFrame Numberに必要なbit数を決定する。

```text
FrameBits = max(1, ceil(log2(TotalQRCount)))
```

Frame Numberは0-basedであるため、Total QR Countを `N` とした場合、

```text
0 ～ N-1
```

を表現できればよい。

したがって `FrameBits` は、0から `N-1` までの値を表現するために必要なbit数となる。

---

# 14. Frame Number

Frame Numberは、現在のFrameを識別する。

bit数はTotal QR Countから決定する。

```text
FrameBits = max(1, ceil(log2(TotalQRCount)))
```

Frame Numberは0-basedであり、0からN-1までを使用する。

```text
0, 1, 2, ... , N-1
```

`0` は予約値ではなく、正規のFrame Numberである。

Total QR Countを超えるFrame Numberは無効。

有効範囲は、

```text
0 <= Frame Number < Total QR Count
```

である。

範囲外のFrame Numberを持つQRは無視する。

例えば、

```text
Total QR Count = 5
```

の場合、

```text
Frame Number = 0
Frame Number = 1
Frame Number = 2
Frame Number = 3
Frame Number = 4
```

が有効であり、

```text
Frame Number = 5
```

以上は無効である。

---

# 15. Data Type

2bit。

```text
00 = Uint8Array
01 = String
10 = 未使用
11 = 未使用
```

旧仕様での `UTF-8 String` / `utf8string` という名称は廃止し、現在は **String** / **string mode** とする。

`10` および `11` は未定義値であり、エラーとして扱う。

Data TypeはFirst QRにのみ存在し、その通信全体に適用される。

後続FrameにはData Typeフィールドを持たせない。

---

# 16. Payload Length

Payloadのbit長を示す。

Payload Length自身のbit数は固定ではなく、Varint形式で決定される。

Payload Lengthを利用することで、PayloadとChecksumの位置を決定できる。

String modeの場合も、Payload LengthはStringという意味での文字数やUTF-8 byte数ではなく、**実際のQR Payload bitstreamのbit長**を示す。

---

# 17. Payload

Payload Lengthで指定されたbit長のPayload。

`Uint8Array` データの場合、byte順はindex順、各byteのbit順はMSB-first。

String modeでは、Payloadは以下の構成とする。

```text
[1bit String Mode][String Data]
```

先頭1bitがString Modeを表す。

String Modeは以下の2種類を定義する。

```text
0 = ASCII Mode
1 = UTF-8 Mode
```

ASCII Modeでは、文字列データをASCIIの7bit値として扱い、**7bit詰め**でPayloadへ格納する。

UTF-8 Modeでは、文字列データをUTF-8 byte列として扱い、**8bit単位**でPayloadへ格納する。

したがって、

```text
String Payload
=
[Mode 1bit]
+
[ASCII 7bit packing または UTF-8 8bit data]
```

となる。

String Modeの1bitもPayloadの一部であり、Payload Lengthに含まれる。

String modeであっても、Payloadの通信・CRC・Frame処理上の基本データは `Uint8Array` / bitstreamとして扱う。

最終的な通信結果を返却するときに、Data Typeに応じてStringへ復元する。

---

# 18. Padding

ビットストリーム全体がbyte境界に到達しない場合、末尾に0bitを追加する。

このpaddingは、

* QR構造上のpadding
* CRC計算時のbyte化のためのpadding

を別のものとして扱わない。

**同一の末尾ゼロpaddingである。**

構造としては、

```text
[... Header ...][Payload][Padding][CRC]
```

となる。

Paddingは必ず `0` でなければならない。

String modeでPayloadが7bit単位のASCIIデータを含む場合も、Payload内部の7bit packingと、Frame末尾のPaddingは別の概念である。

ASCII文字データは7bit単位で連続して詰められ、その後Frame全体がbyte境界に達していない場合にのみ末尾Paddingを追加する。

---

## 18.1 PaddingとCRC位置

Frame Checksumは、Frame構造上、PayloadおよびPaddingの後に配置される。

通常のIntermediate QRでは、

```text
[...][Payload][0-padding][16bit Frame CRC]
```

となる。

Final QRでは、

```text
[...][Payload][0-padding][16bit Frame CRC][32bit Overall CRC]
```

となる。

First QRであってもFinal QRを兼ねる場合は、Final QRと同じくOverall CRCが続く。

ただし、受信側は単純に「最後の16bitをCRC」として逆算するのではなく、前方から順番に構造を解析して、

1. Header
2. Payload Length
3. Payload
4. Padding
5. Frame Checksum
6. Overall Checksum（Finalの場合）

の位置を決定する。

---

# 19. 構文解析と意味的妥当性検証

受信時には、以下を明確に分離する。

## 19.1 構文解析（位置合わせ）

QRの構造を読み、

* 各フィールドがどこにあるか
* Payloadがどこまでか
* Paddingがどこか
* Frame Checksumがどこか
* Finalの場合Overall Checksumがどこか

を決定する。

これはCRCを計算するためにも必要な処理である。

CRC位置まで到達できない、Payload Lengthが構造上成立しない、Varintが不正である等の場合は、CRC検証以前の**構文解析エラー**として扱う。

CRCに到達できていない状態をCRC不一致として扱わない。

---

## 19.2 意味的な妥当性検証（整合性チェック）

構造上の位置が確定した後、

* CRC
* Version
* Data Type
* Frame Number
* Total QR Count
* Payload Length
* Padding
* 通信状態との整合性

などを検証する。

CRC検証のために必要な最小限の構文解析と、その後の意味的検証は別工程として扱う。

---

# 20. Frame Checksum

Frame Checksumは16bit。

アルゴリズム：

```text
CRC-16/CCITT-FALSE
```

パラメータ：

```text
Width     = 16
Poly      = 0x1021
Init      = 0xFFFF
RefIn     = false
RefOut    = false
XorOut    = 0x0000
Check     = 0x29B1
ByteOrder = Big-endian
```

---

# 21. Frame CRCの対象

Frame Checksumは、そのFrame自身のChecksum以前に存在する全bitを対象とする。

基本的には、

```text
[現在のQRのChecksum以前の全bit]
```

が対象となる。

ここでいう「Checksum以前の全bit」には、Payload後に配置された**Frame末尾のPaddingも含む**。

したがって、

```text
[Header]
[Payload]
[Padding]
```

をFrame CRCの対象とする。

First QRの場合はこれだけである。

First QR自身のFrame CRCを、その自身のCRC計算に含めない。

---

# 22. First QR CRCによる通信識別

First QRのFrame CRCは、後続FrameのCRC計算に使用する。

これにより、別途Communication IDを追加せずに、

> 現在受信しているFrameが、どのFirst QRを起点とした通信に属するか

をCRCによって検証できる。

---

# 23. 後続FrameのCRC対象

First QR以外のFrameでは、Frame Checksumの計算対象は、

```text
[現在のQRのChecksum以前の全bit]
+
[First QRのFrame CRC 16bit]
```

とする。

ここで、現在のQRのChecksum以前のbit列には、現在のQRのPaddingを含む。

したがって、処理上は、

```text
Current Frame Data
    =
[Current Header]
+
[Current Payload]
+
[Current Padding]
```

をまずbyte境界までのbyte列として扱い、その後、

```text
[Current Frame Data bytes]
+
[First Frame CRC 2 bytes]
```

をCRC-16/CCITT-FALSEへ入力する。

First Frame CRCを現在のbitstream内部へ挿入するのではなく、**現在QRのCRC対象データを完成させた後、その末尾へFirst CRCの16bitを連結する**。

これにより、現在QRのPaddingは現在QRの構造上のPaddingとしてそのままCRC対象となり、First CRCを途中へ挿入するための追加bit操作は発生しない。

First QRには前提となるFirst CRCが存在しないため、この追加16bitは付加しない。

---

# 24. CRCのbit / byte順

ビットストリーム上の固定長フィールドはMSB-first。

CRC値の格納は指定されたByteOrderに従う。

CRC-16：

```text
ByteOrder = Big-endian
```

CRC-32：

```text
ByteOrder = Big-endian
```

したがってCRC値の上位byteから順番に格納する。

---

# 25. CRC計算時のbit列

CRC対象がbyte境界に一致しない場合は、末尾に0bitを追加してbyte化する。

この0bitはQR構造上のPaddingと同一である。

つまり、

```text
[CRC対象bit列][0-padding]
```

をbyte列としてCRC計算へ渡す。

別途CRC専用のpaddingを追加することはない。

ただし後続Frameでは、現在QRのPaddingを含めて現在QRのCRC対象byte列を確定した後、その後ろへFirst QRのFrame CRC 16bitをBig-endianで連結する。

First CRCを追加するために現在QRのPayloadやPaddingを再配置しない。

---

# 26. Overall Checksum

Final QRにはOverall Checksumが存在する。

Overall Checksumは32bit。

アルゴリズム：

```text
CRC-32/ISO-HDLC
```

パラメータ：

```text
Width     = 32
Poly      = 0x04C11DB7
Init      = 0xFFFFFFFF
RefIn     = true
RefOut    = true
XorOut    = 0xFFFFFFFF
Check     = 0xCBF43926
ByteOrder = Big-endian
```

---

# 27. Overall CRCの対象

Overall CRCは各FrameのHeaderやFrame CRCを対象としない。

全FrameのPayloadをFrame Number順に並べて連結したものを対象とする。

```text
Payload 0
+
Payload 1
+
...
+
Payload N-1
```

これをCRC-32/ISO-HDLCで計算する。

Overall CRCの計算に使用するPayloadは、通信プロトコル上のPayloadデータとして扱われる `Uint8Array` / byte列を基準とする。

String modeであっても、Frame CRCやOverall CRCの検証においては、まずPayloadをbyte列として扱い、文字列そのものを直接CRC計算対象にしない。

String modeのASCII 7bit packingについても、文字列へ復元してからCRCを計算するのではなく、通信上のPayload byte列を対象とする。

---

# 28. Final QRと通信終了の違い

Final QRを受信したことと、通信が終了したことは別である。

```text
Frame Number = Total QR Count - 1
```

であるQRはFinal QR。

しかし、他のFrameがまだ欠落している場合は通信終了ではない。

通信終了条件は、

```text
Frame 0 ～ N-1 の全Frameが揃う
```

ことである。

その時点でPayloadをFrame Number順に連結し、Overall CRCを検証する。

---

# 29. Overall CRCによる通信完了判定

全Frameが揃ったら、

```text
Payload 0
Payload 1
...
Payload N-1
```

を順番に連結する。

その結果に対してCRC-32/ISO-HDLCを計算する。

Final QRに含まれるOverall Checksumと比較する。

```text
一致
→ 通信成功

不一致
→ 通信成功ではない
→ 深刻なエラー
```

Overall CRCは「Final QRを受信した時点」ではなく、「全Frameが揃って終了条件になった時点」で検証する。

Overall CRCが不一致の場合、通信を正常完了とは扱わず、深刻なエラーとして通信を終了する。

---

# 30. 送信処理

送信開始時：

1. Data APIが入力データを解析
2. 必要なFrame数を決定
3. Frame Numberを割り当てる
4. First QRを生成
5. Intermediate QRを生成
6. Final QRを生成
7. 各FrameのCRCを生成
8. Final QRのOverall CRCを生成
9. Browser RuntimeへQRモジュール情報を渡す

Frame Numberは0-basedであるため、最初のFrameには `0` を割り当てる。

送信中は、

```text
0 → 1 → ... → N-1
```

を繰り返す。

```text
N-1 → 0
```

と戻った後も送信を継続する。

---

# 31. 送信停止

送信は自動停止しない。

ユーザーまたはAPIから明示的に停止する。

```text
stop()
```

等のAPIによって停止する。

停止時点が、

* First
* Intermediate
* Final
* 周回途中

のどこであるかは問わない。

送信中に `start()` が再度呼び出された場合、現在の送信状態に関係なく、そのStart要求は無視する。

すでに開始済みの通信を二重に開始しない。

---

# 32. 受信開始前

First QRが読み込まれる前は、正式な通信は開始されていない。

後続QRと思われるデータを受信した場合でも、First QRが存在しない状態では正式な解析・CRC検証を行わない。

ただし、受信したQRデータそのものは一時保存できる。

---

# 33. First QR到着前の一時保存

First QR到着前に受信したQRデータは一時保存する。

保存形式は画像ではなく、

```text
Uint8Array
```

とする。

一時保存数には設定可能な上限を設ける。

上限到達後は追加のQRデータを無視する。

無制限にキューを増加させない。

同じFrame Numberのデータが一時保存領域に既に存在する場合、その重複データは無視する。

---

# 34. First QR前のCRC検証

First QRを受信する前は、後続FrameのCRC検証を行わない。

後続FrameのCRCにはFirst QRのFrame CRCが必要だからである。

したがって、

```text
First QR
    ↓
First CRC確定
    ↓
後続Frame CRC検証可能
```

という順序になる。

---

# 35. First QR受信後の一時保存データ処理

First QRが正常に処理された後は、通信情報を確立する。

その後の新規Camera QRデータを優先して処理する。

以前に一時保存していたQRデータは、処理能力・容量・タイミング等に余裕がある場合に順次処理する。

基本的にはキューの先頭から処理する。

Cameraから新しく受信したQRを処理することが優先される。

新しいCamera QRの処理によって一時保存データが不要になった場合、その一時保存データは削除する。

---

# 36. Frameの重複受信

正常に処理済みのFrameを再受信した場合、毎回完全なパースやCRC検証を行う必要はない。

既処理Frameについては、まず、

* Frame Number
* Payload Length

等の必要最小限の情報のみ確認する。

同一Frame Numberで、既処理時と同じLengthである場合は、既処理データとして無視する。

これはCPUの無駄な消費を防ぐためである。

---

# 37. 既処理Frameの内容変更

既に処理済みのFrame Numberであるにもかかわらず、Payload Length等が以前と異なる場合は、単純に無視しない。

そのFrameについて通常のCRC等の検証を行う。

検証の結果、

```text
完全に正常なデータ
```

である場合は、以前保存していたFrameデータを新しいデータへ交換する。

このような事象は警告対象とし、APIの

```text
onXXXXWarn
```

等のWarning通知機構から通知する。

---

# 38. First QRの再受信

First QRについても、既に確立済みの通信情報が存在する場合は、不要な完全解析を繰り返さない。

必要最小限の情報を確認する。

First QRの内容に差異がある場合は検証対象とする。

特にFirst QRのFrame CRCを比較する。

First QRのFrame Numberは常に `0` である。

---

# 39. First CRCが変更された場合

新しく受信したFirst QRのFrame CRCが、現在通信に使用しているFirst QRのFrame CRCと異なる場合は、現在保存しているFrame 1以降のデータを破棄する。

0-based Frame NumberではFirst QRがFrame 0であるため、破棄対象は、

```text
Frame 1
Frame 2
...
Frame N-1
```

となる。

理由は、後続FrameのCRC計算に使用するFirst CRCが変わるためである。

処理：

```text
新しいFirst QR
    ↓
First CRC比較
    ↓
CRCが異なる
    ↓
Frame 1以降の保存データ破棄
    ↓
新しいFirst QRを通信基準として使用
```

これは通常の「既処理Frameの内容変更」とは別種類の異常・警告として扱う。

APIでは別種類のWarningとして通知する。

---

# 40. Missing Frame

Frameは必ず0からN-1まで揃う必要がある。

例えば、

```text
0 → 1 → 3 → 4
```

と受信した場合、Frame 2が欠落している。

この場合は通信完了とはならない。

送信側は、

```text
0 → 1 → 2 → 3 → 4 → 0 → ...
```

とループしているため、Frame 2が再び送信されるのを待つ。

---

# 41. Out-of-range Frame Number

First QRから取得したTotal QR Countに対して、

```text
Frame Number < 0
```

または、

```text
Frame Number >= Total QR Count
```

となるFrameは無効。

ただしFrame Numberはbitstream上のunsigned値として扱うため、通常の構文上は負値そのものは存在しない。

実際には、

```text
Frame Number >= Total QR Count
```

となるFrameを範囲外として扱い、無視する。

Frame Number `0` は有効なFrame Numberである。

---

# 42. CRCエラー

CRC不一致は、そのQRのデータを有効なFrameとして処理しない。

CRCエラーが発生した場合、そのFrameは破棄・再取得対象とする。

送信側は同じFrameをループ中に再送するため、再受信を待つ。

単発のCRCエラーは、それだけで直ちに通信終了とはしない。

---

# 43. CRCエラー回数

CRCエラー回数は、**連続CRCエラー回数**として管理する。

有効なCRCを持つFrameを受信した場合、連続エラー状態をリセットする。

既に正常処理済みのFrameを再受信し、既処理FrameとしてSkipした場合は、

* 成功として数えない
* 失敗として数えない
* 連続CRCエラー回数を変更しない

。

つまりSkipはCRC成功・失敗のどちらでもない。

```text
CRC Error
→ 連続エラー +1

CRC Success
→ 連続エラーをリセット

Already Processed / Skip
→ 何も変更しない
```

設定された連続CRCエラー回数の閾値を超えた場合、通信を**深刻なエラーとして終了する**。

このエラー終了は通常のCRCエラーによる一時的な再取得とは異なり、通信を継続できない状態として扱う。

---

# 44. CRC検証順序

QRを処理する際、CRCによってデータの整合性を確認できる場合は、意味的な処理を進める前にCRCを確認する。

ただしCRC位置を決定するために必要な構文解析は先に行う。

つまり、

```text
構文解析
    ↓
CRC位置決定
    ↓
CRC検証
    ↓
意味的妥当性検証
    ↓
Frame処理
```

という考え方である。

構文解析自体に失敗してCRC位置を確定できない場合は、CRC不一致として扱わず、構文解析エラーとして扱う。

---

# 45. Invalid QR

以下のようなQRは無効またはエラーとして扱う。

## Version 0

エラー。

## 未対応Version

可能な範囲で解析を試みる。

構造が現在のライブラリで理解できない場合はエラー。

## Undefined Data Type

```text
10
11
```

はエラー。

## Invalid Total QR Count

```text
0
```

など通信情報を確立できない値はエラー。

## Invalid Frame Number

範囲外の場合は無視。

`0` は有効なFrame Numberであるため、Invalid Frame Numberとして扱わない。

## Invalid Payload Length

Payload Lengthの表現が、

* 冗長
* 構造上不正
* Checksum領域まで到達する
* Checksumを確保できない
* その他構造と矛盾する

場合は無効。

Payload Lengthの異常によりChecksum位置そのものを決定できない場合は、CRCエラーではなく構文解析エラーとして扱う。

## Invalid Padding

Paddingが0以外の場合は無効。

---

# 46. Payload Lengthによる構造解析

Payload LengthはChecksum位置を決定するために使用する。

したがって受信側は前方から順番に、

```text
Start
→ Version等
→ Total QR Count
→ Frame Number
→ Data Type
→ Payload Length
→ Payload
→ Padding
→ Frame Checksum
→ Overall Checksum（Finalのみ）
```

と解析する。

単純にQRデータ末尾からCRCを決め打ちすることはしない。

String modeの場合も、Payload LengthによってまずPayloadのbit範囲を決定し、その内部の先頭1bitをString Modeとして解釈する。

---

# 47. Data APIによるQRデータ生成

送信側のData APIはQRプロトコルに従ったbitstreamを生成する。

生成されたQRデータはQRモジュール情報へ変換される。

モジュール情報は黒/白を表すbinary dataとする。

例えば、

```text
[1, 1, 0, 0, ...]
```

のような形式。

Data APIはQRのProtocol DataおよびModule Informationを生成する。

Browser Runtime APIは、そのモジュール情報を実際の画面へ描画する。

String modeの場合、Data APIはStringを指定されたString Modeへ変換し、

```text
[Mode 1bit][String Data]
```

のPayload bitstreamを生成した上でFrame分割を行う。

---

# 48. Browser RuntimeによるQR表示

Browser Runtime APIはData APIが生成したモジュール情報を受け取り、

* Canvas
* DOM
* その他対応する描画手段

によって表示する。

Browser Runtime API自身が通信プロトコルのPayloadやChecksumを生成することはない。

---

# 49. Camera受信

受信時はBrowser Runtime APIがCameraおよびMediaStreamを制御する。

Cameraから取得した画像をData API側へ渡す。

Data API側ではQR画像からQRデータを取得し、その後TypeScript側でプロトコル解析およびFrame結合を行う。

画像処理・QRデコードの一部または全部についてRust/WASMを利用する可能性がある。

Rust/WASMにどこまで処理を移すかは、実装・性能検証後に確定する。

---

# 50. Worker

Workerが利用可能かつ有効化されている場合はWorkerを利用する。

OffscreenCanvas等、Worker側で利用可能なブラウザ機能も活用する。

Workerを利用できない場合、または設定によって無効化されている場合はMain ThreadへFallbackする。

---

# 51. Worker / Main Threadの共通化

Worker用とMain Thread用で共通ロジックを二重実装しない。

共通のRuntime abstraction / wrapperを利用する。

理想的には同一JSファイルを、

```ts
if (isWorkerContext()) {
    runWorker();
} else {
    runMain();
}
```

のようなRuntime判定によってWorker / Main Thread双方で利用できる構成とする。

ただし、Workerの生成方式については、

* Module Worker
* Blob Worker
* その他の方式

を含め、CSP・ESM・CDN等の互換性を考慮して実装時に決定する。

---

# 52. DOM / Canvas API

Browser Runtime APIでは、ユーザーが通信開始・終了を制御できる。

Canvasは以下の指定方法に対応する。

* Canvas Elementそのもの
* Canvas Element ID
* ライブラリ側でCanvasを生成

Canvasサイズはライブラリ設定で変更可能。

未指定の場合は自動調整する。

QRサイズ自体は固定であるため、Canvasサイズの変更・リサイズは基本的に初期設定時に行う。

---

# 53. QR Version

QR Code Versionは設定可能。

対応範囲：

```text
Version 1 ～ Version 40
```

デフォルト：

```text
Version 5
```

ただし、具体的なPayload容量はVersionだけでは固定しない。

実際のQR生成ライブラリおよび設定によって決定される。

---

# 54. Error Correction Level

設定可能。

対応：

```text
L
M
Q
H
```

デフォルト：

```text
M
```

---

# 55. パフォーマンス関連設定

以下は設定可能な候補とする。

* QR表示FPS
* QR切替間隔
* Camera FPS
* QR解析頻度
* QR Version
* Error Correction Level
* QRサイズ
* Worker使用
* その他パフォーマンス関連設定

具体的なデフォルトFPSや切替速度等は、実装および実機検証前には決定しない。

---

# 56. 受信の基本フロー

```text
Camera
  ↓
Browser Runtime API
  ↓
Image
  ↓
Data API / QR Decode
  ↓
QR Uint8Array
  ↓
構文解析
  ↓
First QR？
  ├─ No
  │   ↓
  │ 一時保存
  │
  └─ Yes
      ↓
First QR検証
      ↓
通信情報確立
      ↓
Frame受信
      ↓
CRC検証
      ↓
Frame Number確認
      ↓
Frame保存
      ↓
全Frame揃った？
  ├─ No → 待機
  │
  └─ Yes
      ↓
PayloadをFrame順に結合
      ↓
Overall CRC検証
      ↓
成功
      ↓
通信終了
```

Frame Numberは0-basedであるため、Frame保存は、

```text
Frame 0
Frame 1
...
Frame N-1
```

として行う。

# 57. 送信の基本フロー

```text
Input Data
    ↓
Data API
    ↓
Data Type決定
    ↓
Payload分割
    ↓
Total QR Count決定
    ↓
Frame生成
    ↓
First QR生成
    ↓
First CRC生成
    ↓
後続Frame CRC生成
    ↓
Final QR Overall CRC生成
    ↓
QR Module Data生成
    ↓
Transport API
    ↓
Browser Runtime API
    ↓
QR表示
    ↓
0 → 1 → ... → N-1 → 0 → ...
```

# 58. 通信状態

概念上、受信側には少なくとも以下の状態が存在する。

```text
Idle
  ↓
Waiting for First
  ↓
First Established
  ↓
Receiving
  ↓
Waiting Missing Frames
  ↓
Overall CRC Verification
  ↓
Completed
```

エラー時にはError状態へ遷移する。

ユーザーによる停止・キャンセルも可能とする。

First QR到着前に後続QRが存在しても、通信状態としては正式な通信開始とはみなさない。

Start後に再度Startが呼ばれた場合は、現在の状態に関係なく無視する。

Stop後にStartした場合は、新しい通信として最初から開始する。

---

# 59. First CRCを利用した通信単位

First QRのFrame CRCを後続Frame CRCに含めることで、通信ごとの識別情報を別途追加しない。

通信A：

```text
First CRC = A
```

通信B：

```text
First CRC = B
```

の場合、それぞれの後続Frameは異なるCRC入力を持つ。

したがって、古い通信のFrameを新しい通信へ誤って混在させることを検出できる。

---

# 60. First CRC変更時のFrame破棄

First CRCが変わった場合は、

```text
Frame 1
Frame 2
...
Frame N-1
```

の保持データを破棄する。

Frame 0に相当するFirst QRは新しい通信基準として更新する。

このイベントは通常のFrame更新Warningとは別に通知する。

---

# 61. Warning

通信を即座にエラー終了させるほどではないが、通常とは異なる状態についてWarning通知を行う。

例：

* 既処理Frameの内容変更
* 正常な新データによる既存Frame交換
* First CRC変更による後続Frame破棄
* その他、実装上定義される警告

Warningの具体的なAPI名は実装時に確定する。

---

# 62. Error

通信を継続できない状態ではErrorとして扱う。

例：

* 不正なFormat Version
* 未定義Data Type
* 不正なTotal QR Count
* 構造解析不能
* CRC連続エラーが設定閾値を超過
* Final QRを含む全Frame取得後のOverall CRC不一致
* その他プロトコル上継続不能な状態

特に以下は**深刻なエラー**として扱う。

* First QRの処理における通信確立不能なエラー
* CRC連続エラーが設定された閾値に到達した場合
* Overall CRC不一致
* その他、通信継続不能と定義されたエラー

深刻なエラーが発生した場合は通信をError停止状態へ移行する。

一方、単発のFrame CRC不一致は、連続CRCエラー数の増加対象ではあるが、それだけで深刻なエラーとして即座に停止するものではない。

---

# 63. 予約領域

将来の仕様拡張のため、現在未使用の値を予約する。

Data Type：

```text
10
11
```

Library Format Version：

```text
0
```

など。

未定義領域を将来の機能のために確保し、現行実装では明確に無効値として扱う。

Frame Numberの `0` は予約領域ではなく、0-basedの正規Frame Numberである。

---

# 64. 互換性

Library Format Versionによってプロトコル仕様のバージョンを識別する。

将来仕様が変更された場合でも、Versionによって異なるプロトコルを識別できるようにする。

現在の仕様では、

```text
Library Format Version = 1
```

を使用する。

---

# 65. プロトコル上の重要な順序

QR受信時の基本的な順序は以下とする。

```text
1. QRデータ取得
2. 構文解析
3. 必要な位置情報の確定
4. CRC検証
5. 基本的な値の妥当性確認
6. Frame状態確認
7. Frame保存 / 更新 / Skip
8. 完了判定
9. Overall CRC検証
```

ただし、CRC計算そのものに必要な構造解析はCRC検証より前に行う。

CRC位置まで到達できない構文エラーは、CRCエラーとして扱わない。

---

# 66. 全Frameの保存

受信した正常FrameはFrame Numberをキーとして管理する。

```text
Frame 0
Frame 1
...
Frame N-1
```

の順序で最終的なPayloadを再構築する。

受信順序そのものは最終データの順序を決定しない。

例えば、

```text
0 → 2 → 1 → 4 → 3
```

の順で受信しても、

```text
0 → 1 → 2 → 3 → 4
```

の順にPayloadを結合する。

---

# 67. 受信データの一貫性

同一Frame Numberに対して複数のデータが存在する場合、正常に検証された最新のデータへ交換できる。

ただし、既処理データと異なる内容が検出された場合はWarningを通知する。

CRC不一致データは有効なデータとして交換しない。

Frame Number `0` はFirst QRに対応するため、First CRC変更時の通信基準更新処理と通常のFrame交換処理を区別する。

---

# 68. Communication Completion

通信成功の条件は、

1. First QRを正常に取得
2. Total QR Countを確定
3. Frame 0～N-1をすべて取得
4. 各Frameが有効
5. PayloadをFrame Number順に結合
6. Overall CRCが一致

することである。

すべてを満たした場合のみ通信成功とする。

成功後、受信側は自動的に通信を停止する。

---

# 69. SenderとReceiverの非対称性

送信側は受信側の状態を知らない。

そのため、

```text
Sender
0 → 1 → ... → N-1 → 0 → ...
```

を継続する。

Receiverは必要なFrameを受信し終え、Overall CRCを確認した時点で停止する。

このため、送信側と受信側の停止条件は異なる。

---

# 70. CRCの責務

Frame CRC：

```text
各QR単位の整合性確認
```

First CRCを後続FrameのCRCへ含めることで、

```text
同一通信への所属確認
```

も兼ねる。

Overall CRC：

```text
全Payloadを結合した最終データの整合性確認
```

を担当する。

したがって、

```text
Frame CRC
    ↓
個々のQR / 通信単位の整合性

Overall CRC
    ↓
完成した最終データ全体の整合性
```

という役割分担になる。

---

# 71. CRCの二段階構造

通信全体では、

```text
First QR
  ↓
First Frame CRC
  ↓
Frame 1 CRC ← First CRC
  ↓
Frame 2 CRC ← First CRC
  ↓
...
  ↓
Final Frame CRC ← First CRC
  ↓
全Frame取得
  ↓
Payload連結
  ↓
Overall CRC
```

という構造になる。

Frame Numberは0-basedであるため、First QRはFrame 0である。

---

# 72. 現時点で確定している設計原則

1. 通信は一方向である。
2. ライブラリは送信・受信双方を提供する。
3. 内部データは `Uint8Array` を基本とする。
4. APIはData / Transport / Browser Runtimeの3層に分離する。
5. Data APIはブラウザに依存しない。
6. Browser Runtime APIがCamera、DOM、Canvas、Worker等を扱う。
7. WorkerとMain Threadで共通ロジックを重複実装しない。
8. Workerが利用可能なら利用し、不可ならMain ThreadへFallbackする。
9. QRは0～N-1のFrameに分割される。
10. Senderは0～N-1を無限ループする。
11. Senderは自動停止しない。
12. First QRはStart Bit = 1で識別する。
13. Intermediate / FinalはFrame Numberで判定する。
14. Frame Number = Total QR Count - 1がFinalである。
15. Total QR Count = 1ではFrame 0がFirstかつFinalとなる。
16. ビットストリーム上の通常フィールドはMSB-firstである。
17. Varint内部の6bit DataだけLSB-firstである。
18. Uint8Arrayのbyte順はindex順である。
19. Uint8Array各byteのbit順はMSB-firstである。
20. フィールド間でbyte alignmentを行わない。
21. Paddingは末尾の0bitである。
22. PaddingはCRC計算時のbyte化にも同じものを使用する。
23. Paddingは0以外を許可しない。
24. Frame CRCはCRC-16/CCITT-FALSEである。
25. Frame CRCはChecksum以前の全bitを対象とする。
26. Frame CRCの対象には現在FrameのPaddingも含む。
27. First QR以外のFrame CRCにはFirst QR CRCを追加する。
28. First QR自身には前提CRCを追加しない。
29. 後続Frameでは現在FrameのCRC対象byte列の後ろにFirst CRCを連結する。

# 75. Start / Stop / Error停止のライフサイクル

通信の開始・停止について、以下を正式な状態仕様とする。

## 75.1 Start

Start操作によって通信を開始する。

Start後は、通信状態に応じた通常の送信または受信処理を行う。

Start後に再度Startが呼び出された場合、そのStart操作は無視する。

これは、

* Waiting for First
* First Established
* Receiving
* Waiting Missing Frames
* Overall CRC Verification
* その他のComplete以前の状態

を問わない。

既存通信を途中から再初期化したり、二重に開始したりしない。

---

## 75.2 Stop

Stopは、通信がCompleteになる前であれば、任意の状態から実行できる。

例えば、

* First QR待機中
* First QR確立後
* Frame受信中
* Missing Frame待機中
* その他の通信途中

のいずれからでもStopできる。

Stopによって現在の通信を終了する。

Stop時には現在表示しているQR Canvasをクリアする。

---

## 75.3 Stop後の再Start

Stop後にStartされた場合、以前の通信状態を引き継がない。

新しい通信として最初から開始する。

したがってFrame Numberは再び、

```text
0
```

から開始する。

受信側についても、以前の通信に属するFrame保存状態を新しい通信へ引き継がない。

---

## 75.4 Error停止後の再Start

深刻なエラーによって通信が停止した場合も、次のStartは新しい通信として扱う。

以前の通信状態を引き継がない。

Frame Numberは再び、

```text
0
```

から開始する。

特に、

* First QR関連の深刻なエラー
* CRC連続エラー閾値到達
* Overall CRC不一致

などによってError停止した場合も同様である。

---

# 76. String mode

String modeは、文字列データを通信するためのData Typeである。

旧仕様で使用していた `utf8string` という名称は使用せず、正式名称を `string` とする。

String modeでは、通信Payloadを以下の構成で保持する。

```text
[1bit String Mode]
[String Data]
```

先頭1bitが文字列データの符号化方式を表す。

```text
0 = ASCII Mode
1 = UTF-8 Mode
```

この1bitはString modeのPayloadの一部である。

---

## 76.1 ASCII Mode

ASCII Modeでは、String DataをASCII文字として扱う。

各文字を7bitのASCII値として表現し、それらを7bit単位で連続してPayloadへ詰める。

例えばASCII文字が、

```text
A
B
C
```

の場合、それぞれのASCII値を7bitで表現し、

```text
0100001
0100010
0100011
```

のように連続して配置する。

ASCII Modeでは8bit byte境界ごとに文字を格納するのではなく、**7bit packing**を行う。

そのため、ASCII文字列全体のbit長は、

```text
7 × 文字数
```

となる。

その後、Frame全体のbitstreamがbyte境界に到達しない場合に、通常のFrame Paddingを末尾へ追加する。

ASCII Modeの7bit packingによるbit列と、Frame末尾のPaddingは別の概念である。

---

## 76.2 UTF-8 Mode

UTF-8 Modeでは、String DataをUTF-8へ変換したbyte列として扱う。

各UTF-8 byteは8bit単位でPayloadへ格納する。

例えばUTF-8 byte列が、

```text
0x41 0x42 0x43
```

の場合、

```text
01000001 01000010 01000011
```

としてPayloadへ格納する。

UTF-8 ModeではASCII Modeのような7bit packingは行わない。

---

## 76.3 String ModeとPayload Length

String modeのPayloadは、

```text
[1bit Mode][String Data]
```

で構成される。

したがってPayload Lengthは、Modeの1bitを含めた**Payload全体のbit長**を示す。

ASCII Modeの場合、

```text
Payload Length
=
1 + (7 × ASCII文字数)
```

を基本とする。

UTF-8 Modeの場合、

```text
Payload Length
=
1 + (8 × UTF-8 byte数)
```

を基本とする。

Frame分割によってPayloadが複数Frameへ分かれる場合でも、通信全体として構成されたString PayloadのbitstreamをFrameへ分割する。

---

## 76.4 String modeのFrame分割

String modeのPayloadは、文字列として再分割するのではなく、生成されたPayload bitstreamを通信可能なFrameへ分割する。

したがって、ASCII ModeではFrame境界が7bit文字境界と一致するとは限らない。

同様に、UTF-8 ModeではFrame境界がUTF-8文字境界と一致するとは限らない。

Frame分割・再結合では、Payload bitstreamをそのまま順番通りに扱う。

通信全体のPayloadをFrame Number順に連結することで、元のString Payload bitstreamを復元する。

---

## 76.5 String modeの検証

String modeであっても、Frame CRCおよびOverall CRCの検証時には、文字列へ変換してから検証しない。

検証対象は通信プロトコル上のPayloadを表す `Uint8Array` / bitstreamとする。

つまり、

```text
QR
 ↓
bitstream
 ↓
Payload
 ↓
Uint8Array / byte列として検証
 ↓
CRC
```

の順序で処理する。

文字列への変換は、通信全体の検証が成功し、最終的なData APIの結果を構築するときに行う。

---

## 76.6 String modeの復元

全Frameが揃い、Overall CRCが成功した後、String modeの場合はPayloadを再構築する。

まず先頭1bitからString Modeを取得する。

```text
0
→ ASCII Mode

1
→ UTF-8 Mode
```

その後、String Modeに応じて残りのString Dataを復元する。

ASCII Modeでは7bit単位で文字を復元する。

UTF-8 Modeでは8bit単位のUTF-8 byte列として復元し、UTF-8 Stringへ変換する。

復元に失敗する場合は、Stringとしてのデータ妥当性エラーとして扱う。

---

# 77. Frame NumberとFrameBitsの確定定義

Frame Numberは0-basedである。

Total QR Countを `N` とした場合、

```text
有効Frame Number
=
0 ～ N-1
```

である。

FrameBitsは、

```text
FrameBits = max(1, ceil(log2(N)))
```

とする。

この定義ではFrame Number `0` が有効値であり、0を予約する必要はない。

例えば、

```text
N = 1
→ FrameBits = 1
→ Frame Number = 0

N = 2
→ FrameBits = 1
→ Frame Number = 0, 1

N = 3
→ FrameBits = 2
→ Frame Number = 0, 1, 2

N = 4
→ FrameBits = 2
→ Frame Number = 0, 1, 2, 3

N = 5
→ FrameBits = 3
→ Frame Number = 0 ～ 4
```

となる。

Frame Numberとして使用しないbitパターンが存在する場合、その値はTotal QR Countとの比較によって範囲外として扱う。

例えば、

```text
N = 5
FrameBits = 3
```

の場合、3bitでは、

```text
000 = 0
001 = 1
010 = 2
011 = 3
100 = 4
101 = 5
110 = 6
111 = 7
```

を表現できるが、

```text
5, 6, 7
```

は `N-1 = 4` を超えるため無効である。

# 78. 深刻なエラーの扱い

通信上、単なる一時的な受信失敗と、通信を継続できない深刻なエラーを区別する。

## 通常のエラー

例えば単発のFrame CRC不一致は、通常の受信エラーとして扱う。

```text
CRC不一致
    ↓
Frame破棄
    ↓
同じFrameの再送を待つ
```

この時点では通信自体を停止しない。

---

## 深刻なエラー

以下は深刻なエラーとして扱う。

* First QRの通信確立に必要な重大なエラー
* CRC連続エラーが設定閾値に到達した場合
* 全Frame取得後のOverall CRC不一致
* その他、プロトコル上継続不能と定義されたエラー

深刻なエラーが発生した場合は、通信をError状態へ移行して停止する。

---

## 深刻なエラー後の再Start

Error停止後にStartされた場合は、以前の通信を復旧するのではなく、新しい通信として開始する。

受信側は以前のFrame保存状態を利用しない。

送信側も以前の送信位置を利用しない。

新しい通信は、

```text
Frame 0
```

から開始する。

---

# 79. Start操作の重複

Startは通信開始操作である。

すでに通信が開始されている場合、Startを再度呼び出しても何も変更しない。

```text
Start
  ↓
通信開始

Start
  ↓
無視
```

これは通信状態に依存しない。

特に、

```text
Waiting for First
First Established
Receiving
Waiting Missing Frames
Overall CRC Verification
```

等の状態でStartを呼び出しても、現在の通信を再初期化しない。

CompleteまたはStop/Errorによって通信が終了した後のStartは、新規通信開始として扱う。

---

# 80. Stop操作

Stopは明示的な通信終了操作である。

Complete前であれば、どの通信途中状態からでも実行できる。

```text
任意の通信途中状態
        ↓
      stop()
        ↓
       Idle
```

Stopによって、

* 現在の通信状態
* 現在の送信位置
* 受信Frame状態
* 待機中の通信処理

を終了する。

受信側では現在保持している通信Frameを次の通信へ引き継がない。

送信側では現在のFrame位置を次の通信へ引き継がない。

また、Stop時にはQR表示Canvasをクリアする。

---

# 81. Stop / Error後の状態初期化

Stopまたは深刻なErrorによって通信が終了した場合、次回Startは新規通信として扱う。

したがって、

```text
旧通信
    ↓
Stop / Error
    ↓
状態破棄
    ↓
Start
    ↓
新通信
```

となる。

受信側では、

```text
旧通信のFrame 0～N-1
```

を新通信へ引き継がない。

送信側では、

```text
旧通信のFrame位置
```

を新通信へ引き継がない。

新しい送信はFrame 0から始まる。

新しい受信はWaiting for Firstから開始する。

# 82. v6で確定した追加事項のまとめ

v6では、v5までのプロトコルを維持したうえで、以下を正式に確定した。

### Frame Number

```text
0 ～ N-1
```

の0-based。

`0`は予約値ではなく正規のFrame Number。

### First / Final

```text
First
→ Frame 0

Final
→ Frame N-1
```

`N = 1`の場合はFrame 0がFirstかつFinal。

### FrameBits

```text
FrameBits = max(1, ceil(log2(N)))
```

0-based Frame Numberにより、この式で0～N-1を表現する。

### String mode

正式名称：

```text
string
```

Payload：

```text
[1bit Mode][String Data]
```

Mode：

```text
0 = ASCII
1 = UTF-8
```

ASCII：

```text
7bit packing
```

UTF-8：

```text
8bit単位
```

### CRC

現在FrameのChecksum以前の全bitにはPaddingを含める。

後続Frameでは、

```text
Current Frame Data
+
First Frame CRC
```

の順でCRC-16へ入力する。

First CRCは現在Frameのbitstream内部へ挿入しない。

### Error

単発CRCエラーは通信継続。

連続CRCエラー閾値到達は深刻なエラー。

Overall CRC不一致も深刻なエラー。

### Start

通信開始後のStartは状態に関係なく無視。

### Stop

Complete前なら任意の状態から実行可能。

Stop時にはQR Canvasをクリア。

### Restart

Stop後または深刻なError停止後のStartは新規通信。

送信はFrame 0から開始。

受信はWaiting for Firstから開始。

旧通信の状態は引き継がない。
