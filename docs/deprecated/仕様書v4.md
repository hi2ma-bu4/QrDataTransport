# QrDataTransport 仕様書 v4

## 1. 概要

QrDataTransport は、ブラウザ間で QR コードを高速に切り替えながら表示・撮影することでデータを転送する TypeScript + Rust/WASM ライブラリである。

物理的な通信媒体は QR コードであり、実際の通信方向は一方向である。

ただし、ライブラリとしては以下の両方を実装する。

- 送信機能
- 受信機能

内部で扱うデータの基本形式は `Uint8Array` とする。

---

## 2. 基本方針

### 2.1 通信方式

送信側は QR を一定順序で繰り返し表示する。

```text
1 → 2 → 3 → ... → N
↑                 ↓
└─────────────────┘
```

送信側は受信側の状態を知ることができないため、ACK による同期は行わない。

したがって、送信側はユーザーが停止するまで、

```text
1 → 2 → ... → N → 1 → 2 → ... → N → ...
```

とループする。

---

### 2.2 通信方向

物理的な通信は一方向である。

```text
Sender
  ↓
QR表示
  ↓
Camera
  ↓
Receiver
```

受信側から送信側への ACK や制御情報の返却は、本プロトコルでは行わない。

---

### 2.3 内部データ形式

ライブラリ内部の基本データ形式は `Uint8Array` とする。

現在のプロトコルで定義する Data Type は以下の2種類。

| 値 | Data Type |
|---|---|
| `0b00` | `Uint8Array` |
| `0b01` | UTF-8 String |
| `0b10` | 未使用 |
| `0b11` | 未使用 |

`0b10` と `0b11` は将来の拡張用として予約する。

---

# 3. API アーキテクチャ

QrDataTransport は以下の3層に分離する。

```text
┌──────────────────────────────────────────────────────┐
│                  QrDataTransport                     │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │             Browser Runtime API                │  │
│  │ Camera / DOM / Canvas / Worker                 │  │
│  │ MediaStream / OffscreenCanvas / Timing         │  │
│  └──────────────────────┬─────────────────────────┘  │
│                         │                            │
│  ┌──────────────────────▼─────────────────────────┐  │
│  │                Transport API                   │  │
│  │ Send / Receive / Timing / State / Error        │  │
│  └──────────────────────┬─────────────────────────┘  │
│                         │                            │
│  ┌──────────────────────▼─────────────────────────┐  │
│  │                  Data API                      │  │
│  │ Uint8Array / Protocol / Frame / QR Data        │  │
│  │ Checksum / Split / Reconstruction / WASM       │  │
│  └──────────────────────┬─────────────────────────┘  │
│                         │                            │
│                         ▼                            │
│                    Rust / WASM                       │
│                                                      │
└──────────────────────────────────────────────────────┘
```

---

## 3.1 Data API

Browser に依存しないデータ処理層。

担当範囲：

- `Uint8Array` の処理
- 入力データの変換
- データ分割
- Frame 生成
- Frame Number の生成
- QR プロトコルデータの生成
- QR プロトコルデータの解析
- Payload Length の生成・解析
- Checksum の計算・検証
- Frame の再構成
- QR データ生成
- QR データ解析
- QR Module Data の生成
- Image からの QR 解析
- WASM との連携

Data API は、実際の Camera や DOM の操作を行わない。

---

## 3.2 Transport API

Data API と Browser Runtime API の間に位置する通信制御層。

担当範囲：

- Send / Receive
- Frame の進行制御
- QR の表示順序制御
- QR 切替タイミング
- Data API と Browser Runtime API の橋渡し
- 通信状態管理
- 通信開始・終了制御
- タイムアウト・エラー処理
- 受信Frame管理
- 重複Frame管理
- 欠落Frame管理

---

## 3.3 Browser Runtime API

実際のブラウザ API を扱う層。

担当範囲：

- Camera
- MediaStream
- DOM
- Canvas
- OffscreenCanvas
- Worker
- Timing
- QR Module Data の表示
- Image の取得
- ユーザーによる通信開始・終了操作との接続
- Canvas の取得・設定

以下を混同しない。

```text
「何を送るか」
→ Data API

「通信をどう進行させるか」
→ Transport API

「ブラウザ上でどう動かすか」
→ Browser Runtime API
```

---

# 4. データ処理の責務

以下はそれぞれ分離する。

```text
QRデータ生成 ≠ QR表示
QRデータ解析 ≠ Camera制御
通信プロトコル ≠ Worker制御
データ再構成 ≠ DOM操作
```

---

# 5. 入力データ

現在のプロトコルで正式に定義する入力形式は以下。

### Uint8Array

そのまま内部データとして使用する。

Data Type：

```text
0b00
```

### UTF-8 String

UTF-8 に変換して内部的には `Uint8Array` として扱う。

Data Type：

```text
0b01
```

その他のデータ形式については、現時点ではプロトコル上の Data Type として定義しない。

将来的に `0b10` / `0b11` を使用して追加することができる。

---

# 6. QR プロトコル

1回の送信データは複数の QR Frame に分割される。

QR の種類は以下の3種類。

1. First QR
2. Intermediate QR
3. Final QR

---

## 6.1 First QR

First QR は以下の順序で構成する。

```text
[Start Bit]
[Library Format Version]
[Total QR Count]
[Frame Number]
[Data Type]
[Payload Length]
[Payload]
[Frame Checksum]
```

---

## 6.2 Intermediate QR

Intermediate QR は以下の順序で構成する。

```text
[Start Bit]
[Frame Number]
[Payload Length]
[Payload]
[Frame Checksum]
```

---

## 6.3 Final QR

Final QR は以下の順序で構成する。

```text
[Start Bit]
[Frame Number]
[Payload Length]
[Payload]
[Frame Checksum]
[Overall Checksum]
```

---

# 7. QR 各フィールド

## 7.1 Start Bit

サイズ：

```text
1 bit
```

値：

| QR | Start Bit |
|---|---|
| First QR | `1` |
| Intermediate QR | `0` |
| Final QR | `0` |

---

## 7.2 Library Format Version

サイズ：

```text
4 bits
```

現在の初期値：

```text
0b0001
```

つまり Version 1 から開始する。

```text
0b0000
```

は未使用であり、不正とする。

将来的にプロトコル構造を変更する場合、この Version を使用する。

---

## 7.3 Total QR Count

サイズ：

```text
16 bits
```

値：

```text
1 ～ 65535
```

送信データ全体を構成する QR の総数を表す。

このフィールドは First QR のみに存在する。

Total QR Count が成立しない値の場合、通信をエラーとする。

---

## 7.4 Frame Number

Frame Number は QR の順番を表す。

有効な Frame Number は、

```text
1 ～ Total QR Count
```

とする。

Frame Number のbit数は以下で決定する。

```text
FrameBits = max(1, ceil(log2(TotalQRCount)))
```

Frame Number は、その数値をそのまま2進数化して格納する。

例：

```text
TotalQRCount = 1
→ FrameBits = 1

TotalQRCount = 2
→ FrameBits = 1

TotalQRCount = 3
→ FrameBits = 2

TotalQRCount = 4
→ FrameBits = 2

TotalQRCount = 5
→ FrameBits = 3
```

Frame Number が `0` または `Total QR Count` を超える場合は範囲外であるため、その Frame を無視する。

---

# 8. Data Type

サイズ：

```text
2 bits
```

定義：

```text
00 = Uint8Array
01 = UTF-8 String
10 = 未使用
11 = 未使用
```

`10` / `11` を受信した場合は不正とする。

---

# 9. Payload Length

Payload Length は可変長整数として格納する。

基本構造は以下。

```text
[Continuation][Data]
```

サイズ：

```text
1 bit + 6 bits = 7 bits / group
```

Data は6bit。

Continuation は1bit。

---

## 9.1 Continuation

```text
1 = 後続のgroupが存在する
0 = このgroupが最後
```

---

## 9.2 格納方式

数値は下位6bitから順に格納する。

LEB128 に近い方式であり、LSB-first とする。

Payload Length は符号なし整数。

最小bit数で表現する。

冗長な表現は認めない。

---

## 9.3 Payload Length = 0

0 は以下の7bitで表現する。

```text
[continuation=0][data=000000]
```

---

## 9.4 例：64

64 は、

```text
64 = 0b1000000
```

であるため、

```text
[continuation=1][data=000000]
[continuation=0][data=000001]
```

となる。

合計14bit。

---

## 9.5 冗長表現

最小bit数で表現されていない Payload Length は不正とする。

例えば、本来1groupで表現可能な値を2group以上で表現するなど、冗長な表現を受信した場合はフレームを不正とする。

---

## 9.6 Payload Length のbit数

理論上、QR Version 40 の最大Payloadが約2953 byte程度である場合、現在の想定ではPayload Lengthは7bitまたは14bitで表現可能である。

ただし、実際のPayload容量は以下により変動する。

- QR Version
- Error Correction Level
- QR生成ライブラリ
- 本プロトコルのヘッダサイズ
- その他の実装上の制約

そのため、仕様としてPayload Lengthを7bitまたは14bitに限定しない。

21bit以上の表現能力も残す。

---

# 10. Bit Packing

QR Frame 内の各フィールドは、byte境界を考慮せず連続したbit列として結合する。

例えば、

```text
[1bit]
[4bit]
[16bit]
[FrameBits]
[2bit]
[PayloadLength]
[Payload]
[16bit]
```

をそれぞれの境界でbyte alignmentすることはしない。

すべてのbitを連続して結合する。

---

## 10.1 Byte化

連結後のbit数が8の倍数でない場合、末尾に `0` を追加して8bit単位にする。

```text
[bit][bit][bit]...[bit]
                    ↓
              末尾を0埋め
                    ↓
[byte][byte][byte]...
```

途中にpaddingは入れない。

---

## 10.2 Decode

Decode時には、各フィールドの仕様上のbit数から開始位置を計算する。

前のフィールドがbyte境界で終わっていなくても問題ない。

例えば、

```text
Field A
    3 bits

Field B
    6 bits
```

の場合、Field B はbyteの途中から開始する。

Decode側でbit offsetを補正して必要なbitを取得する。

したがって、

```text
フィールド境界 = byte境界
```

である必要はない。

---

# 11. Frame Checksum

Frame Checksum は、

```text
16 bits
```

とする。

アルゴリズム：

```text
CRC-16/CCITT-FALSE
```

---

## 11.1 Checksum対象

Frame Checksum より前に存在する**すべてのbit**を対象とする。

つまり First QR では、

```text
[Start Bit]
[Library Format Version]
[Total QR Count]
[Frame Number]
[Data Type]
[Payload Length]
[Payload]
```

が対象。

Intermediate QR では、

```text
[Start Bit]
[Frame Number]
[Payload Length]
[Payload]
```

が対象。

Final QR では、

```text
[Start Bit]
[Frame Number]
[Payload Length]
[Payload]
```

が対象。

Final QR の Overall Checksum は Frame Checksum の対象に含めない。

---

## 11.2 CRC入力のbyte化

CRC対象が8bitの倍数でない場合は、対象bit列の末尾を `0` で埋めてbyte化してからCRCを計算する。

これは通常のFrame byte化と同じ規則である。

---

# 12. 後続Frameの通信整合性

後続Frameが、現在受信しているFirst QRを起点とする通信に属することを検証するため、First QRのFrame Checksumを後続FrameのCRC計算に利用する。

First QRのCRCを、

```text
FirstFrameCRC
```

とする。

Intermediate QRおよびFinal QRのFrame Checksum計算時には、First QRのCRC情報をCRC計算の前提に含める。

これにより、別の通信からFrameが混入した場合でも整合性を検証できるようにする。

この仕組みを利用することで、別途Communication IDを設けずに通信単位の整合性を確認する。

---

# 13. Overall Checksum

Final QR のみ Overall Checksum を持つ。

サイズ：

```text
32 bits
```

アルゴリズム：

```text
CRC-32/ISO-HDLC
```

---

## 13.1 Overall Checksumの対象

Overall Checksum は、QRのraw bit列やFrame Headerを対象としない。

各FrameのPayloadをFrame Number順に並べ、結合したデータを対象とする。

```text
Payload 1
+ Payload 2
+ ...
+ Payload N
```

として得られたデータに対してCRC-32/ISO-HDLCを計算する。

---

# 14. 送信順序

送信側は必ず以下の順序でFrameを生成・表示する。

```text
1 → 2 → 3 → ... → N
```

Nまで到達した後は、

```text
N → 1
```

と戻り、再び、

```text
1 → 2 → ... → N
```

を繰り返す。

---

## 14.1 Senderの終了条件

送信側は、全Frameを1回送信した時点では終了しない。

ユーザーが明示的にStop APIを呼び出すことで終了する。

```text
start()
 ↓
1 → 2 → ... → N
 ↑             ↓
 └──── loop ───┘
 ↓
userによるstop()
 ↓
停止
```

Frame進行度にかかわらず、Stopが呼ばれた時点で停止する。

したがって、ユーザー側のJavaScriptでStop処理を発火しない場合、送信は仕様上永続的にループする。

---

# 15. Receiverの通信開始

ReceiverはFirst QRを受信することで正式に通信を開始する。

First QRを受信する前にIntermediate QRまたはFinal QRを受信した場合、それらを即座には解析しない。

代わりにQRデータを一時保存する。

```text
QR受信
 ↓
First QRか？
 ├─ Yes → 検証・通信開始
 └─ No  → Uint8Arrayとして一時保持
```

---

# 16. First QR受信前の一時保持

画像そのものは保持しない。

QRとして取得されたデータを `Uint8Array` として保持する。

---

## 16.1 保持数

一時保持できる枚数には設定可能な上限を設ける。

上限を超えた場合、それ以上のQRは保持しない。

キューが無制限に増加することはない。

---

## 16.2 重複

同じ Frame Number のQRを複数保持しない。

同一Frame Numberが既に保持されている場合、新しいものは無視する。

---

## 16.3 CRC検証

First QRを受信する前は、後続QRのCRC検証を行わない。

理由：

後続QRのCRC検証にはFirst QRを起点とする通信整合性情報が必要であるため。

---

## 16.4 First QR受信後

First QRの検証が完了し、通信情報が確立した後、First QR受信前に一時保持していたQRを解析する。

ただし、処理優先順位はカメラから新しく取得したQRを優先する。

概念的には、

```text
First QR受信後

カメラからの新規QR
        ↓
      最優先
        ↓
   通常処理

余力がある場合
        ↓
一時保持データの先頭
        ↓
    パース処理
```

とする。

---

## 16.5 一時保持データの破棄

First QR受信後、カメラからの新規QRが先に処理されたことによって一時保持データが不要になった場合、その保留データは削除する。

不要になった保留データを後から処理してはならない。

---

## 16.6 First QRが来ない場合

First QRが永遠に受信できない場合、ライブラリは自動的に通信終了とはしない。

ユーザーが明示的に中断APIを呼び出すまで待機する。

---

# 17. Frame受信

ReceiverはFrame Numberによって受信済みFrameを管理する。

---

## 17.1 重複Frame

既に受信・処理済みのFrame Numberを再び受信した場合、そのFrameは無視する。

例：

```text
1 → 2 → 2 → 3
```

の場合、2回目の `2` は処理しない。

---

## 17.2 欠落Frame

必要なFrame Numberが未受信の場合、そのFrameが再び送信されるまで待機する。

例：

```text
1 → 2 → 4 → 5
```

の場合、

```text
3
```

が不足しているため通信は完了しない。

Senderはループしているため、後続の送信サイクルで `3` が再び送られる。

---

## 17.3 Frame Number範囲外

Frame Numberが、

```text
1 ～ TotalQRCount
```

の範囲外の場合、そのFrameは無視する。

これは通信エラーとはしない。

---

# 18. QRの不正判定

受信したQRは、まずFrame Checksumを検証する。

不正なデータを使って後続の解析・状態更新を行わないことを目的とする。

---

## 18.1 CRC不一致

Frame CRCが一致しない場合、そのQRは不正として扱う。

そのQRを受理せず、再取得を待つ。

---

## 18.2 CRCエラーの連続判定

CRCエラーには設定可能な規定回数を設ける。

ただし、この回数は**連続したCRCエラー**として数える。

処理済みFrameなど、CRCエラーではなく既に処理済みとしてSkipされるQRは、連続CRCエラー数に影響しない。

判定は、

```text
CRC成功
→ 成功として扱う

CRC失敗
→ 連続CRCエラー数を+1

既に処理済みでSkip
→ 連続CRCエラー数を変更しない
```

とする。

規定回数の連続CRCエラーが発生した場合、通信エラーとして終了する。

---

# 19. その他の不正条件

## 19.1 Library Format Version = 0

Version `0` は未使用であるためエラーとする。

---

## 19.2 未対応のLibrary Format Version

現在のライブラリが対応するVersionより新しいVersionを受信した場合、可能な範囲で解析を試行する。

解析した結果、現在のライブラリが理解できるフォーマットとして整合しない場合はエラーとする。

---

## 19.3 未定義Data Type

```text
0b10
0b11
```

など、現在定義されていないData Typeを受信した場合はエラーとする。

---

## 19.4 Payload Lengthの不正

Payload Lengthが、Frame Checksumを含む残りのデータ領域を超える場合はエラーとする。

つまり、

```text
Payload
```

がFrame Checksumの領域まで食い込む、またはChecksumを成立させるために必要なbit数が不足する場合は不正とする。

また、Payload Lengthが最小表現になっていない冗長表現も不正とする。

---

## 19.5 Total QR Countの不正

Total QR Countは16bitで表現されるが、有効範囲は、

```text
1 ～ 65535
```

とする。

これを成立させられない場合は通信エラーとする。

---

# 20. 通信完了

全Frame Number、

```text
1 ～ TotalQRCount
```

が揃った時点でPayloadをFrame Number順に結合する。

```text
Payload 1
↓
Payload 2
↓
...
↓
Payload N
```

その結合結果に対してOverall Checksumを計算する。

---

## 20.1 Overall Checksum一致

計算結果とFinal QRに含まれるOverall Checksumが一致した場合、通信を正常完了とする。

```text
全Frame取得
 ↓
Payload結合
 ↓
CRC-32/ISO-HDLC
 ↓
Overall Checksum比較
 ↓
一致
 ↓
受信成功
 ↓
Receiver自動停止
```

---

## 20.2 Overall Checksum不一致

一致しない場合は通信を正常完了とはしない。

最終的な受信データとして返却してはならない。

---

# 21. Receiverの終了

受信側は、Overall Checksumまで正常に検証できた場合、自動的に停止する。

また、First QRが来ない場合や通信中に問題が発生した場合でも、ユーザーが明示的に中断できるAPIを提供する。

---

# 22. Browser Runtime API

Browser Runtime APIはブラウザ固有の処理を担当する。

---

## 22.1 Sender側

Sender側ではBrowser Runtime APIはData APIからQR Module Dataを受け取る。

Data APIがQRデータを生成し、それをQR Module Dataに変換する。

概念：

```text
User Data
 ↓
Data API
 ↓
QR Protocol Data
 ↓
QR Module Data
   [1,1,0,0,...]
 ↓
Transport API
 ↓
Browser Runtime API
 ↓
Canvas / DOM
 ↓
表示
```

Browser Runtime APIはQRプロトコル自体を生成する責務を持たない。

---

## 22.2 Receiver側

Receiver側ではBrowser Runtime APIはCameraからImageを取得する。

概念：

```text
Camera
 ↓
Browser Runtime API
 ↓
Image
 ↓
Data API
 ↓
Worker
 ↓
WASM
 ↓
QR detection / decoding
 ↓
QR data
 ↓
TypeScript
 ↓
Uint8Array
 ↓
Transport API
```

Browser Runtime APIはQRのプロトコル解析を担当しない。

---

# 23. Worker

Workerが利用可能であり、かつ設定で有効化されている場合、Workerを利用する。

Workerが利用できない場合、またはユーザーが無効化した場合はMain Threadで処理する。

---

## 23.1 共通処理

Worker版とMain Thread版で共通処理を重複実装しない。

共通のRuntime abstraction / wrapperを使用し、処理本体を共有する。

---

## 23.2 Workerファイル

Consumer側から別Worker JavaScriptファイルを明示的に指定する必要がない構成を目標とする。

# 31. Receiverの状態概念

Receiverは概念的に以下の状態を持つ。

```text
Idle
 ↓
Waiting for First QR
 ↓
Receiving
 ↓
Completed
```

エラー時には通信エラー状態へ遷移する。

また、ユーザーによるStop / Cancelによって任意の状態から停止できる。

---

# 32. First QRによる通信確立

First QRは通信の基準情報を確立する。

First QRから以下を取得する。

- Library Format Version
- Total QR Count
- Frame Number
- Data Type
- Payload Length
- Payload
- First Frame CRC

後続FrameではFirst QRを起点とするCRC整合性を利用する。

これにより、別通信のFrame混入を検出する。

---

# 33. 受信済みFrame管理

ReceiverはFrame NumberをキーとしてFrameを管理する。

```text
Frame 1
Frame 2
Frame 3
...
Frame N
```

同じFrame Numberが既に正常受信済みの場合、そのFrameは処理しない。

このような「既に処理済みなのでSkip」というケースは、CRCエラーの連続失敗カウントには影響しない。

---

# 34. 通信エラー

以下のような場合、通信エラーとして終了する。

- 規定回数のCRC連続失敗
- Total QR Countが不正
- 未定義Data Type
- 不正なPayload Length
- その他、現在のプロトコルとして成立しないフォーマット

一方、単純なFrame欠落やFrame Numberの重複、範囲外Frameなどは、それ自体では通信エラーとはしない。

---

# 35. 再取得

CRC不一致のQRは受理せず、同じFrame Numberが後で再び送信されることを待つ。

Senderは同じFrame列をループしているため、欠落・CRCエラーが発生したFrameを再取得できる。

---

# 36. 通信完了判定

通信完了には以下のすべてを満たす必要がある。

1. First QRが正常に確立されている。
2. Total QR Countが確定している。
3. Frame Number `1..N` がすべて揃っている。
4. PayloadをFrame Number順に結合できる。
5. Final QRのOverall Checksumと、結合Payloadから計算したCRC-32/ISO-HDLCが一致する。

すべてを満たした場合のみ受信成功とする。

---

# 37. API責務の原則

以下の責務分離を維持する。

```text
Data API
    ↓
「データそのものをどう扱うか」

Transport API
    ↓
「通信をどう進行させるか」

Browser Runtime API
    ↓
「ブラウザ上でどう実行するか」
```

Data APIはブラウザAPIに依存しない。

Browser Runtime APIはQRプロトコルの意味を理解する必要がない。

Transport APIはCameraやDOMを直接操作しない。

# 43. 現在のプロトコル全体

現在の基本構造は以下。

## First QR

```text
[Start: 1bit]
[Format Version: 4bit]
[Total QR Count: 16bit]
[Frame Number: FrameBits]
[Data Type: 2bit]
[Payload Length: variable]
[Payload: variable]
[Frame CRC: 16bit]
```

## Intermediate QR

```text
[Start: 1bit]
[Frame Number: FrameBits]
[Payload Length: variable]
[Payload: variable]
[Frame CRC: 16bit]
```

## Final QR

```text
[Start: 1bit]
[Frame Number: FrameBits]
[Payload Length: variable]
[Payload: variable]
[Frame CRC: 16bit]
[Overall CRC: 32bit]
```

# 44. 現在のFrame処理全体

Sender：

```text
Data
 ↓
Split
 ↓
Frame 1
 ↓
Frame 2
 ↓
...
 ↓
Frame N
 ↓
1へ戻る
 ↓
loop
```

Receiver：

```text
Camera
 ↓
QR decode
 ↓
First QR?
 ├─ No
 │   ↓
 │  Uint8Arrayとして一時保持
 │
 └─ Yes
     ↓
    First QR検証
     ↓
    通信確立
     ↓
    保留QRを処理
     ↓
    新規QRを優先処理
     ↓
    Frame CRC検証
     ↓
    Frame Number確認
     ↓
    重複ならSkip
     ↓
    Payload保存
     ↓
    全Frame取得?
      ├─ No → 待機
      └─ Yes
           ↓
       Payload結合
           ↓
       Overall CRC
           ↓
       一致?
        ├─ No → 未完了/エラー処理
        └─ Yes
             ↓
          受信成功
             ↓
          自動停止
```

# 45. 設計上の重要な原則まとめ

1. 内部データ形式は `Uint8Array` を基本とする。
2. 通信は物理的に一方向である。
3. ACKによる同期は行わない。
4. Senderは `1..N` を永続的にループする。
5. SenderはユーザーのStopでのみ終了する。
6. ReceiverはFirst QRを通信確立の起点とする。
7. First QR前の後続QRはUint8Arrayとして一時保持する。
8. 一時保持数には上限を設ける。
9. First QR前は後続QRのCRC検証を行わない。
10. First QR確立後は新規Cameraデータを保留データより優先する。
11. 不要になった保留データは削除する。
12. Frame Numberで重複を排除する。
13. 欠落FrameはSenderの次回ループで再取得する。
14. Frame Number範囲外は無視する。
15. Frame CRCはCRC-16/CCITT-FALSEを使用する。
16. Frame CRCはChecksum以前の全bitを対象とする。
17. CRC入力のbyte化では末尾を0埋めする。
18. bit列はフィールド境界でbyte alignmentしない。
19. Frame Numberのbit数は `max(1, ceil(log2(TotalQRCount)))`。
20. Payload Lengthは6bit data + 1bit continuationのLSB-first方式。
21. Payload Lengthは符号なし整数かつ最小表現とする。
22. 冗長なPayload Length表現は不正とする。
23. CRC不一致は再取得する。
24. CRCエラーの規定回数判定は連続失敗で行う。
25. 既に処理済みとしてSkipされたQRはCRC連続失敗数を変更しない。
26. 規定回数の連続CRC失敗で通信エラーとする。
27. First QRのCRCを後続FrameのCRC整合性の前提に含める。
28. Communication IDを別途設けず、First QR起点のCRC整合性を利用する。
29. Overall CRCはCRC-32/ISO-HDLCを使用する。
30. Overall CRCはFrame PayloadをFrame Number順に結合した結果を対象とする。
31. 全Frame取得だけでは通信完了としない。
32. Overall CRC一致をもって正常完了とする。
33. Receiverは正常完了後に自動停止する。
34. ユーザーはReceiverをAPIで途中中断できる。
35. Library Format Version `0` は不正とする。
36. 未対応Versionは可能な範囲で試行し、整合しなければエラーとする。
37. 未定義Data Typeはエラーとする。
38. Payload LengthがChecksum領域まで到達する場合はエラーとする。
39. Total QR Countは1〜65535を有効とする。
40. Data APIはBrowser APIから独立する。
41. Transport APIは通信進行を担当する。
42. Browser Runtime APIはCamera / DOM / Canvas / Worker等を担当する。
43. Sender側Browser Runtime APIにはQR Module Dataを渡す。
44. Receiver側Browser Runtime APIからData APIへImageを渡す。
45. Worker利用可能時はWorkerを利用できる。
46. Worker無効時・利用不可時はMain Threadへfallbackする。
47. Worker/Main Threadで共通処理を重複実装しない。
48. OffscreenCanvasを利用可能な構成とする。
49. CanvasはElement / ID / ライブラリ生成の方式を扱える構成とする。
50. Canvasサイズは設定可能で、未指定時は自動リサイズする。
51. QR Versionは1〜40、デフォルト5。
52. Error Correction LevelはL/M/Q/H、デフォルトM。
53. 実効Payload容量・速度・FPS等の性能値は実測前に固定しない。
54. Rust/WASMの詳細な処理分担は性能検証後に決定する。
55. QR Module Data / Imageの具体的型は今後決定する。
56. Transport API / Runtime APIの具体的TypeScriptシグネチャは今後決定する。
