# QrDataTransport 仕様書 v2

## 1. 概要

**QrDataTransport** は、Webブラウザ間でカメラとQRコードを利用してデータ通信を行うライブラリである。

送信側ブラウザでQRコードを高速に切り替えて表示し、受信側ブラウザがカメラを使用して連続的にQRコードを読み取ることで、複数のQRコードに分割されたデータを転送する。

実装言語は以下を使用する。

* TypeScript
* Rust / WebAssembly

通信自体は一方向とするが、ライブラリは送信・受信の双方に対応する。

---

# 2. 設計方針

QrDataTransportは、以下の3層に分離する。

```text
┌─────────────────────────────────────┐
│ Browser Runtime API                 │
│                                     │
│ Camera / DOM / Canvas / Worker      │
│ MediaStream / Timing                │
└─────────────────┬───────────────────┘
                  │
                  ▼
┌─────────────────────────────────────┐
│ Transport API                       │
│                                     │
│ 通信制御・フレーム送受信              │
└─────────────────┬───────────────────┘
                  │
                  ▼
┌─────────────────────────────────────┐
│ Data API                            │
│                                     │
│ Uint8Array / QR Data / Protocol     │
│ Frame / Checksum / Reconstruction   │
└─────────────────────────────────────┘
```

各層の責務を明確に分離し、QRデータ処理とブラウザ固有処理が直接依存しない構造とする。

---

# 3. API構成

公開APIは以下の3つを基本とする。

1. Data API
2. Transport API
3. Browser Runtime API

---

# 4. Data API

## 4.1 目的

通信するデータおよびQR通信データを扱う低レイヤーAPI。

ブラウザ、DOM、Camera、Canvas、Worker等のブラウザ実行環境には依存しない。

内部の基本データ形式は `Uint8Array` とする。

---

## 4.2 主な責務

* `Uint8Array` の受け取り
* データ分割
* フレーム生成
* フレーム番号管理
* QR用通信データ生成
* QR通信データ解析
* フレーム再構成
* フレームchecksum
* 全体checksum
* データフォーマット管理
* 通信終了情報の処理

---

## 4.3 データフロー

### 送信

```text
Uint8Array
    ↓
Data Format
    ↓
Protocol Encode
    ↓
Frame Split
    ↓
QR Data
```

### 受信

```text
QR Data
    ↓
Protocol Decode
    ↓
Frame Validation
    ↓
Frame Reconstruction
    ↓
Overall Checksum Validation
    ↓
Uint8Array
```

---

## 4.4 入力データ形式

内部形式は `Uint8Array` とする。

High-level APIでは複数の入力形式を受け付ける。

対応形式の詳細は今後決定する。

候補：

* `Uint8Array`
* `ArrayBuffer`
* `string`
* JSON
* `Blob`
* その他

入力データは最終的に `Uint8Array` へ変換する。

---

## 4.5 データフォーマットMode

通信データには元データの形式を識別するためのモード情報を含める。

概念：

```text
┌────────────────────┐
│ Data Format Mode   │
├────────────────────┤
│ Data Payload       │
└────────────────────┘
```

受信側ではModeを利用して、必要に応じて元のデータ形式へ復元する。

具体的なMode一覧および値は未決定。

# 5. QR通信プロトコル

## 5.1 フレーム

1つのQRコードを1フレームとして扱う。

大きなデータは複数のQRフレームへ分割する。

```text
Data
 │
 ├── Frame 0 → QR
 ├── Frame 1 → QR
 ├── Frame 2 → QR
 ├── ...
 └── Frame N → QR
```

---

## 5.2 QRフレーム構造

各QRには通信に必要な制御情報を含める。

現時点で想定する情報：

* Protocol Version
* Session / Transfer ID
* Frame Number
* Total Frame Count または終了情報
* Data Format Mode
* Payload
* Frame Checksum
* 終端情報

具体的なバイトレイアウトは未決定。

---

## 5.3 Frame Number

各フレームにフレーム番号を付与する。

```text
Frame 0
Frame 1
Frame 2
Frame 3
...
Frame N
```

受信側ではフレーム番号を利用して、

* 順序確認
* 欠落検出
* 重複検出
* フレーム再構成

を行う。

フレーム番号のサイズは未決定。

---

# 6. Checksum

Checksumは2段階で使用する。

## 6.1 Frame Checksum

各QRフレームにChecksumを含める。

```text
┌────────────────────┐
│ Header             │
│ Frame Information  │
│ Payload            │
│ Frame Checksum     │
└────────────────────┘
```

受信側はQR単位でChecksumを検証する。

これにより、個別QRデータの破損を検出する。

Checksumアルゴリズムおよびサイズは未決定。

---

## 6.2 Overall Checksum

通信データ全体についてChecksumを生成する。

最終QRに全体Checksumを含める。

```text
Frame 0
Frame 1
Frame 2
...
Frame N
   └── Overall Checksum
```

受信側は全フレームを再構成した後、全体Checksumを検証する。

これにより通信全体の整合性を確認する。

Checksumアルゴリズムおよびサイズは未決定。

---

# 7. Transport API

## 7.1 目的

Data APIとBrowser Runtime APIの橋渡しを行い、実際のQR通信を制御するAPI。

Data APIが「データをどうQR通信データに変換するか」を担当するのに対し、Transport APIは「それをどのように通信として進行させるか」を担当する。

---

## 7.2 主な責務

* 送信処理
* 受信処理
* フレーム送信順序の管理
* QR切り替えタイミングの管理
* QRフレームの受け渡し
* 通信開始・終了管理
* 通信状態管理
* タイムアウト
* エラー処理
* Data APIとRuntime APIの接続

---

## 7.3 送信

```text
Input Data
    ↓
Data API
    ↓
QR Frame
    ↓
Transport API
    ↓
Browser Runtime API
    ↓
QR Display
```

---

## 7.4 受信

```text
Camera
    ↓
Browser Runtime API
    ↓
QR Data
    ↓
Transport API
    ↓
Data API
    ↓
Reconstructed Data
```

---

# 8. Browser Runtime API

## 8.1 目的

ブラウザ固有の実動作を管理するAPI。

通信データや通信プロトコル自体には依存しない。

---

## 8.2 主な責務

* Camera
* `MediaStream`
* DOM
* Canvas
* OffscreenCanvas
* Worker
* QR表示
* カメラ映像取得
* フレーム取得タイミング
* ブラウザAPIとの接続

---

## 8.3 QR表示

Transport APIから渡されたQRデータを、ブラウザ上へ表示する。

```text
Transport API
      ↓
Browser Runtime API
      ↓
QR Renderer
      ↓
DOM / Canvas / その他描画環境
```

QRデータの内容そのものを決定する責務は持たない。

---

## 8.4 QR取得

カメラから取得した映像を処理し、QR通信データをTransport APIへ渡す。

```text
Camera
   ↓
Browser Runtime API
   ↓
Image Processing
   ↓
QR Detection / Decode
   ↓
QR Data
   ↓
Transport API
```

# 9. Worker / OffscreenCanvas

可能な環境ではWorkerおよびOffscreenCanvasを利用する。

以下の場合はMain Threadへフォールバックする。

* Workerが使用できない
* OffscreenCanvasが使用できない
* 利用者がWorkerを無効化している
* 実行環境上の理由でWorkerを使用できない

---

## 9.1 Runtime構造

```text
Browser Runtime API
        │
        ├── Main Runtime
        │
        └── Worker Runtime
```

Main Runtime：

```text
Main Thread
    ├── Camera
    ├── Canvas
    └── Processing
```

Worker Runtime：

```text
Main Thread
    │
    └── Worker
          ├── OffscreenCanvas
          └── Processing
```

---

## 9.2 処理の共通化

Worker使用時とMain Thread使用時で同じ処理を二重実装しない。

Runtime固有処理と共通処理の間に抽象化層を設ける。

```text
             Common Processing
                    │
             Runtime Wrapper
              /           \
             /             \
    Main Runtime       Worker Runtime
          │                   │
          ▼                   ▼
    Main Thread             Worker
```

WorkerとMain Threadで異なるのは、主にブラウザ実行環境への接続部分とする。

---

# 10. Workerの提供方式

利用者がWorker用JavaScriptファイルを別途指定する必要がない構成を目標とする。

同一JavaScriptファイルから自身をWorkerとして起動できる構造とする。

概念：

```ts
if (isWorkerContext()) {
    runWorker();
} else {
    runMain();
}
```

具体的なWorker生成方式は未決定。

候補：

* Module Worker
* Blob Worker
* その他

CSP、ESM、CDN等との互換性については実装時に検討する。

以下について調査・実測する。

# 15. API間の責務境界

重要な設計原則として、以下を分離する。

```text

Data API

「通信をどう進行させるか」
        ↓

「ブラウザ上でどう動かすか」
        ↓

```

特に以下を混在させない。

```text

    ≠

QRデータ解析
    ≠

    ≠

    ≠

```

# 20. v2での設計原則

1. ライブラリ名は `QrDataTransport` とする。
2. 通信自体は一方向とする。
3. ライブラリは送信・受信の双方を実装する。
4. 内部データ形式は `Uint8Array` とする。
5. High-level APIでは複数の入力データ形式を利用可能にする。
6. 通信データ内にデータフォーマットModeを含める。
7. QR 1枚を1フレームとして扱う。
8. 各QRフレームにフレーム番号を含める。
9. 各QRフレームにFrame Checksumを含める。
10. 最終QRにOverall Checksumを含める。
11. データ処理とブラウザ実動作を分離する。
12. 公開APIをData API、Transport API、Browser Runtime APIの3層に分離する。
13. Data APIはブラウザ固有APIへ依存しない。
14. Browser Runtime APIはCamera、DOM、Canvas、Worker等のブラウザ実動作を管理する。
15. Transport APIはData APIとBrowser Runtime APIを接続する。
16. Worker使用時と非使用時で共通処理を二重実装しない。
17. Worker / OffscreenCanvasが利用可能な場合は利用できる構造とする。
18. Workerが使用できない場合、または設定で無効化された場合はMain Threadへフォールバックする。
19. 速度・QRサイズ等の主要パラメータは設定可能とする。
20. Rust/WASMの担当範囲は性能調査後に決定する。
21. 将来的な双方向通信への拡張を妨げない設計とする。

```

このv2では、特に **「QRデータを扱うData API」と「QRを実際に画面へ出したりカメラから取得したりするRuntime API」が完全に別物**として扱えるようになっています。
```
