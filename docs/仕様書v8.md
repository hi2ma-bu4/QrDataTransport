# QrDataTransport 仕様書 v8

## 1. 概要

QrDataTransport は、ブラウザ間で QR コードを高速に切り替え表示・撮影することでデータ通信を行うためのライブラリである。

実際の物理通信は QR コードを介した**一方向通信**である。

ただしライブラリとしては、

* 送信機能
* 受信機能

の双方を提供する。

内部で扱う基本データ型は `Uint8Array` とする。

---

# 2. API構成

APIは以下の3層に分離する。

```text
┌──────────────────────────────────────────────────────┐
│                  QrDataTransport                     │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │             Browser Runtime API                │  │
│  │ Camera / DOM / Canvas / Worker                 │  │
│  │ MediaStream / OffscreenCanvas / Timing         │  │
│  └──────────────────────┬─────────────────────────┘  │
│                         │                            │
│  ┌──────────────────────▼─────────────────────────┐  │
│  │                Transport API                   │  │
│  │ Send / Receive / Timing / State / Error        │  │
│  └──────────────────────┬─────────────────────────┘  │
│                         │                            │
│  ┌──────────────────────▼─────────────────────────┐  │
│  │                  Data API                      │  │
│  │ Uint8Array / Protocol / Frame / QR Data        │  │
│  │ Checksum / Split / Reconstruction / WASM       │  │
│  └──────────────────────┬─────────────────────────┘  │
│                         │                            │
│                         ▼                            │
│                    Rust / WASM                       │
│                                                      │
└──────────────────────────────────────────────────────┘
```

## 2.1 Data API

通信データおよび QR プロトコルそのものを扱う。

ブラウザに依存しない。

主な責務：

* `Uint8Array` の処理
* String / `Uint8Array` のデータ変換
* データ種別の管理
* データの分割
* Frame生成
* QR用ビットデータ生成
* QRデータの解析
* Frameの再構築
* Frame CRC検証
* Overall CRC検証
* QRデコード後データの処理
* Rust / WASMによる処理

Data APIは実際のカメラ、DOM、Canvas等を直接操作しない。

Data APIは通信状態やFrame保存状態などのTransport上のデータを保持する責務を持たない。

Frame Numberのパースや範囲確認等、データそのものに対する解析・検証はData APIが担当する。

ただし、解析結果を利用したFrameの保持、既存Frameの上書き、CRC連続エラー回数の管理、通信状態の変更等はTransport APIが担当する。

---

## 2.2 Transport API

通信そのものを管理する。

主な責務：

* Send開始
* Send停止
* Receive開始
* Receive停止
* Frame順序管理
* 送信状態管理
* 受信状態管理
* QR切替タイミング管理
* Data APIとBrowser Runtime APIの橋渡し
* 通信エラー管理
* 通信完了管理
* 受信Frameの保持
* 既存FrameのSkip / 更新判断
* CRC連続エラー回数の管理
* Warning / Error callback

Data APIから受け取った解析結果を用いて通信状態を管理する。

---

## 2.3 Browser Runtime API

実際のブラウザ機能を扱う。

主な対象：

* Camera
* MediaStream
* DOM
* Canvas
* OffscreenCanvas
* Worker
* Timing

Browser Runtime APIは、Data APIが生成した QR のモジュール情報を実際に表示する。

また受信時には、Cameraから取得した画像をData API側へ渡す。

Browser Runtime API自身は、PayloadやChecksumなどの通信プロトコルを生成・解析しない。

---

# 3. 基本データ形式

内部の基本データ形式は `Uint8Array` とする。

文字列を扱う場合は String mode に従って処理する。

Data APIから通信結果を返却する際は、データ本体だけではなくデータ型情報も返却する。

```ts
{
    type: "Uint8Array" | "string",
    data: Uint8Array | string
}
```

これにより、Transport API等が返却されたデータの型を推測する必要はない。

Stringとして扱う場合でも、QR Payloadの生成・分割・CRC検証・再構築等の内部処理では、Payloadを基本的に `Uint8Array` / bitstreamとして扱う。

Stringへの変換は、通信全体の検証およびPayload再構築が完了した後に行う。

---

# 4. QR通信方式

通信対象データを複数の QR に分割する。

QRは必ず以下のFrame Numberによって構成される。

```text
0 → 1 → ... → N-1
```

ただし送信側は受信側の状態を知ることができないため、1回送信しただけでは停止しない。

送信中は以下のように無限ループする。

```text
0 → 1 → ... → N-1 → 0 → 1 → ... → N-1 → ...
```

送信を停止するのはユーザー/APIによる `stop` 操作のみとする。

送信側は、全Frameを一度送信したことを理由に自動停止しない。

Frame Numberは0-basedであり、通信上の最初のFrameを `0` とする。

---

# 5. QRの種類

QRには以下の3種類の構造が存在する。

* First QR
* Intermediate QR
* Final QR

ただし、QRごとに完全に別の構造を持たせるのではなく、基本的なフィールドを順番に配置する。

## First QR

```text
[Start Bit]
[Library Format Version]
[Total QR Count]
[Frame Number]
[Data Type]
[Payload Length]
[Payload]
[Padding]
[Frame Checksum]
```

## Intermediate QR

```text
[Start Bit]
[Frame Number]
[Payload Length]
[Payload]
[Padding]
[Frame Checksum]
```

## Final QR

```text
[Start Bit]
[Frame Number]
[Payload Length]
[Payload]
[Padding]
[Frame Checksum]
[Overall Checksum]
```

---

# 6. First / Intermediate / Final の判定

## 6.1 First QR

First QRの判定条件は以下の2条件である。

```text
Start Bit = 1
Frame Number = 0
```

この2条件を満たすQRをFirst QRとして扱う。

First QRには通信全体を解析するために必要な情報が含まれる。

First QRのFrame Numberは必ず `0` である。

Start BitおよびFrame Number以外の情報をFirst判定のために重複して使用する必要はない。

その他の値に問題がある場合は、その後の整合性検証によって検出する。

---

## 6.2 Intermediate / Final

First QRを受信して通信情報が確立された後は、Frame Numberによって判定する。

```text
Frame Number < Total QR Count - 1
    → Intermediate

Frame Number = Total QR Count - 1
    → Final
```

したがって、Final QRには特別な専用識別bitを追加しない。

Frame Numberは0-basedであるため、Total QR Countを `N` とした場合の有効Frame Numberは、

```text
0 ～ N-1
```

となる。

---

## 6.3 Total QR Count = 1

`Total QR Count = 1` の場合、

```text
Frame Number = 0
Total QR Count = 1
```

となるため、そのQRは、

* First
* Final

の両方に該当する。

構造は既存のフィールド順を崩さず、必要なフィールドを順番に配置することで整合性を取る。

実装上はQRを読みながら条件に応じて必要なフィールドを処理することで、通常の複数Frame通信と `Total QR Count = 1` の両方を扱える。

---

# 7. ビットストリーム

すべてのフィールドは、1つの連続したビットストリームとして扱う。

フィールド境界でbyte alignmentを行わない。

例えば、

```text
[4bit][16bit][3bit][...]
```

のようにフィールドが連続する場合、次のフィールドは前のフィールドの直後から開始する。

フィールドの開始位置がbyte境界に一致するとは限らない。

Payloadについても、Frame間の分割はbit単位で行う。

文字単位、byte単位でFrameを分割することはしない。

---

# 8. ビット順

ビットストリーム上の通常の固定長フィールドは **MSB-first** とする。

つまり数値を指定bit数で表現する場合、上位bitから順番にビットストリームへ配置する。

例：

```text
8bit value = 0x96

0x96
= 10010110
```

ビットストリーム上では、

```text
1 0 0 1 0 1 1 0
```

の順番で配置する。

---

# 9. Uint8Array のbyte / bit順

`Uint8Array` のPayloadは、

* byte順：`Uint8Array` のindex順
* 各byte内部のbit順：MSB-first

とする。

例えば、

```ts
new Uint8Array([
    0x96,
    0x2A,
    0xF0
])
```

は、

```text
10010110 00101010 11110000
```

の順番でビットストリームへ配置する。

String modeにおいても、最終的なPayload検証・CRC処理ではPayloadを `Uint8Array` / byte列として扱う。

---

# 10. Varint

`Payload Length` は可変長整数として格納する。

1グループは7bitで構成される。

```text
[Continuation Bit][6bit Data]
```

* Continuation Bit = `1`

  * 後続グループが存在する
* Continuation Bit = `0`

  * このグループが最後

---

## 10.1 Varint内部のbit順

通常のビットストリームはMSB-firstだが、**Varint内部の6bit DataのみLSB-first**とする。

つまり、

```text
通常フィールド
→ MSB-first

Varintの6bit Data
→ LSB-first
```

という例外的な構造になる。

このLSB-firstはVarintの内部表現にのみ適用され、Varintフィールド全体をMSB-first/LSB-firstに反転するものではない。

---

## 10.2 6bit Data

各グループの6bit Dataには、値の下位6bitから格納する。

次のグループには、その次の6bitを格納する。

これはLEB128に類似した方式である。

---

## 10.3 最小表現

Payload Lengthは最小bit数で表現する。

冗長な表現は禁止する。

例えば0は、

```text
[Continuation=0][Data=000000]
```

の7bitで表現する。

---

## 10.4 64の例

64の場合、

```text
64 = 0b1000000
```

なので、

```text
[1][000000][0][000001]
```

となり、合計14bitとなる。

---

# 11. Start Bit

Start Bitは1bit。

```text
First QR:
1

First QR以外:
0
```

Start Bitは通信開始を識別するために使用する。

First QRが読み込まれていない状態では、後続QRについて通信を正式には開始しない。

---

# 12. Library Format Version

4bit。

現在の仕様では、

```text
0b0001
```

から開始する。

```text
0b0000
```

は未使用。

Version 0は無効なQRとして扱う。

ライブラリが対応していない将来Versionについては、可能な範囲で構造を解析する。

ただし、現在のライブラリが理解できない構造である場合は通信エラーとする。

未知Versionであっても、構造を理解でき、通信を継続できる場合はWarningとして扱う。

---

# 13. Total QR Count

Total QR Countは、通信全体に含まれるQRの総数を表す。

有効なTotal QR Countの範囲は、

```text
1 ～ 65536
```

である。

Total QR Countの格納領域は16bitとする。

ただし、Total QR Countそのものを16bitのunsigned整数として格納するのではなく、以下の符号化を行う。

```text
StoredTotalQRCount = TotalQRCount - 1
```

したがって、

```text
StoredTotalQRCount = 0
    → Total QR Count = 1

StoredTotalQRCount = 1
    → Total QR Count = 2

...

StoredTotalQRCount = 65535
    → Total QR Count = 65536
```

となる。

受信時は、

```text
Total QR Count = StoredTotalQRCount + 1
```

として復元する。

StoredTotalQRCountは16bitの固定長フィールドとして、ビットストリーム上ではMSB-firstで格納する。

したがって、StoredTotalQRCountとして使用できる値は、

```text
0 ～ 65535
```

であり、これによりTotal QR Countとして、

```text
1 ～ 65536
```

を表現できる。

Total QR CountはFirst QRにのみ存在する。

Total QR Countは通信全体のFrame数を表し、この値からFrame Numberに必要なbit数を決定する。

```text
FrameBits = max(1, ceil(log2(TotalQRCount)))
```

Frame Numberは0-basedであり、Total QR Countを `N` とした場合、

```text
0 ～ N-1
```

を有効なFrame Numberとして使用する。

例えば、

```text
Total QR Count = 1
→ StoredTotalQRCount = 0
→ FrameBits = 1
→ 有効Frame Number = 0

Total QR Count = 2
→ StoredTotalQRCount = 1
→ FrameBits = 1
→ 有効Frame Number = 0, 1

Total QR Count = 3
→ StoredTotalQRCount = 2
→ FrameBits = 2
→ 有効Frame Number = 0, 1, 2

Total QR Count = 65536
→ StoredTotalQRCount = 65535
→ FrameBits = 16
→ 有効Frame Number = 0 ～ 65535
```

Total QR Countが `0` になることはない。

StoredTotalQRCountの16bit値は、0～65535の範囲を超えることができないため、Total QR Countとして65537以上を表現することはできない。

受信時に復元したTotal QR Countが有効範囲 `1 ～ 65536` を外れることは、通常の16bit格納値からは発生しない。


---

# 14. Frame Number

Frame Numberは、現在のFrameを識別する。

bit数はTotal QR Countから決定する。

```text
FrameBits = max(1, ceil(log2(TotalQRCount)))
```

Frame Numberは0-basedであり、0からN-1までを使用する。

```text
0, 1, 2, ... , N-1
```

`0` は予約値ではなく、正規のFrame Numberである。

Total QR Countを超えるFrame Numberは無効。

有効範囲は、

```text
0 <= Frame Number < Total QR Count
```

である。

範囲外のFrame Numberを持つQRは無視する。

例えば、

```text
Total QR Count = 5
```

の場合、

```text
Frame Number = 0
Frame Number = 1
Frame Number = 2
Frame Number = 3
Frame Number = 4
```

が有効であり、

```text
Frame Number = 5
```

以上は無効である。

Frame Numberとして使用されない余剰bitパターンは、範囲外Frame Numberとして無視する。

---

# 15. Data Type

2bit。

```text
00 = Uint8Array
01 = String
10 = 未使用
11 = 未使用
```

旧仕様での `UTF-8 String` / `utf8string` という名称は廃止し、現在は **String** / **string mode** とする。

`10` および `11` は将来拡張用の予約領域であり、現行仕様では未定義値としてエラー扱いする。

Data TypeはFirst QRにのみ存在し、その通信全体に適用される。

後続FrameにはData Typeフィールドを持たせない。

---

# 16. Payload Length

Payloadのbit長を示す。

Payload Length自身のbit数は固定ではなく、Varint形式で決定される。

Payload Lengthを利用することで、PayloadとChecksumの位置を決定できる。

String modeの場合も、Payload LengthはStringという意味での文字数やUTF-8 byte数ではなく、**実際のQR Payload bitstreamのbit長**を示す。

各FrameにおけるPayload Lengthは、そのFrameに含まれるPayloadのbit数を表す。

Payload Length `0` は有効であり、長さ0のPayloadを許可する。

Payload Lengthにはプロトコル上の意図的な上限を設けない。

---

# 17. Payload

Payload Lengthで指定されたbit長のPayload。

`Uint8Array` データの場合、byte順はindex順、各byteのbit順はMSB-first。

PayloadのFrame分割はbit単位で行う。

したがって、Frame境界でbyte境界を維持する必要はない。

String modeでは、Payloadは以下の構成とする。

```text
[1bit String Mode][String Data]
```

先頭1bitがString Modeを表す。

String Modeは以下の2種類を定義する。

```text
0 = ASCII Mode
1 = UTF-8 Mode
```

String Modeの1bitはPayloadの一部であり、Payload Lengthに含まれる。

String modeの通信全体のPayloadでは、先頭の1bitのみがString Modeを表す。

Frame 1以降のFrameでは、このString Mode bitを再掲しない。

通信全体として生成されたString Payload bitstreamをそのままFrame単位に分割するため、後続Frameは前Frameから続くPayload bitstreamをそのまま保持する。

ASCII Modeでは、文字列データをASCIIの7bit値として扱い、**7bit詰め**でPayloadへ格納する。

ASCIIとして使用できる値の範囲は、

```text
0x00 ～ 0x7F
```

である。

ASCII範囲外の文字・値をASCII Modeとして送信しようとした場合は、送信側でエラーとする。

UTF-8 Modeでは、文字列データをUTF-8 byte列として扱い、**8bit単位**でPayloadへ格納する。

UTF-8 Modeでは、Payload内のbyte列について、現在存在するUnicode文字として妥当かどうかを別途検証しない。

ただし、UTF-8 Modeとして定義された8bit単位の構造を満たさない等、プロトコル上のbit数・構造そのものが成立しない場合はエラーとする。

String modeであっても、Payloadの通信・CRC・Frame処理上の基本データは `Uint8Array` / bitstreamとして扱う。

最終的な通信結果を返却するときに、Data Typeに応じてStringへ復元する。

---

# 18. Padding

ビットストリーム全体がbyte境界に到達しない場合、末尾に0bitを追加する。

Paddingを計算する対象は、先頭の1bitフラグからそのFrameのPayload末尾までを含むFrame構造上のbit列である。

つまり、

```text
[Start Bit]
[Header]
[Payload]
```

までのbit数を基準としてbyte boundaryを計算し、その末尾に0bitを追加する。

このpaddingは、

* QR構造上のpadding
* CRC計算時のbyte化のためのpadding

を別のものとして扱わない。

**同一の末尾ゼロpaddingである。**

構造としては、

```text
[... Header ...][Payload][Padding][CRC]
```

となる。

Paddingは必ず `0` でなければならない。

String modeでPayloadが7bit単位のASCIIデータを含む場合も、Payload内部の7bit packingと、Frame末尾のPaddingは別の概念である。

ASCII文字データは7bit単位で連続して詰められ、その後Frame全体がbyte境界に達していない場合にのみ末尾Paddingを追加する。

---

## 18.1 PaddingとCRC位置

Frame Checksumは、Frame構造上、PayloadおよびPaddingの後に配置される。

通常のIntermediate QRでは、

```text
[...][Payload][0-padding][16bit Frame CRC]
```

となる。

Final QRでは、

```text
[...][Payload][0-padding][16bit Frame CRC][32bit Overall CRC]
```

となる。

First QRであってもFinal QRを兼ねる場合は、Final QRと同じくOverall CRCが続く。

ただし、受信側は単純に「最後の16bitをCRC」として逆算するのではなく、前方から順番に構造を解析して、

1. Header
2. Payload Length
3. Payload
4. Padding
5. Frame Checksum
6. Overall Checksum（Finalの場合）

の位置を決定する。

QRに含めるデータをFrameのビット列として扱う場合、そのFrameの構造上のbit列にはChecksumも含まれる。

---

# 19. 構文解析と意味的妥当性検証

受信時には、以下を明確に分離する。

## 19.1 構文解析（位置合わせ）

QRの構造を読み、

* 各フィールドがどこにあるか
* Payloadがどこまでか
* Paddingがどこか
* Frame Checksumがどこか
* Finalの場合Overall Checksumがどこか

を決定する。

これはCRCを計算するためにも必要な処理である。

CRC位置まで到達できない、Payload Lengthが構造上成立しない、Varintが不正である等の場合は、CRC検証以前の**構文解析エラー**として扱う。

CRCに到達できていない状態をCRC不一致として扱わない。

---

## 19.2 意味的な妥当性検証（整合性チェック）

構造上の位置が確定した後、

* CRC
* Version
* Data Type
* Frame Number
* Total QR Count
* Payload Length
* Padding
* 通信状態との整合性

などを検証する。

CRC検証のために必要な最小限の構文解析と、その後の意味的検証は別工程として扱う。

エラーの分類は、通信継続への影響によって行う。

* Critical Error：通信を継続できない
* 通常Error：異常だが無視・再取得等によって本進行を継続できる
* Warning：異常は存在するが通信進行そのものへの影響がない

---

# 20. Frame Checksum

Frame Checksumは16bit。

アルゴリズム：

```text
CRC-16/CCITT-FALSE
```

パラメータ：

```text
Width     = 16
Poly      = 0x1021
Init      = 0xFFFF
RefIn     = false
RefOut    = false
XorOut    = 0x0000
Check     = 0x29B1
ByteOrder = Big-endian
```

---

# 21. Frame CRCの対象

Frame Checksumは、そのFrame自身のChecksum以前に存在する全bitを対象とする。

基本的には、

```text
[現在のQRのChecksum以前の全bit]
```

が対象となる。

ここでいう「Checksum以前の全bit」には、Payload後に配置された**Frame末尾のPaddingも含む**。

したがって、

```text
[Header]
[Payload]
[Padding]
```

をFrame CRCの対象とする。

First QRの場合はこれだけである。

First QR自身のFrame CRCを、その自身のCRC計算に含めない。

---

# 22. First QR CRCによる通信識別

First QRのFrame CRCは、後続FrameのCRC計算に使用する。

これにより、別途Communication IDを追加せずに、

> 現在受信しているFrameが、どのFirst QRを起点とした通信に属するか

をCRCによって検証できる。

First CRCは通信単位を識別するための情報として扱う。

---

# 23. 後続FrameのCRC対象

First QR以外のFrameでは、Frame Checksumの計算対象は、

```text
[現在のQRのChecksum以前の全bit]
+
[First QRのFrame CRC 16bit]
```

とする。

ここで、現在のQRのChecksum以前のbit列には、現在のQRのPaddingを含む。

したがって、処理上は、

```text
Current Frame Data
    =
[Current Header]
+
[Current Payload]
+
[Current Padding]
```

をまずbyte境界までのbyte列として扱い、その後、

```text
[Current Frame Data bytes]
+
[First Frame CRC 2 bytes]
```

をCRC-16/CCITT-FALSEへ入力する。

First Frame CRCを現在のbitstream内部へ挿入するのではなく、**現在QRのCRC対象データを完成させた後、その末尾へFirst CRCの16bitを連結する**。

これにより、現在QRのPaddingは現在QRの構造上のPaddingとしてそのままCRC対象となり、First CRCを途中へ挿入するための追加bit操作は発生しない。

First QRには前提となるFirst CRCが存在しないため、この追加16bitは付加しない。

---

# 24. CRCのbit / byte順

ビットストリーム上の固定長フィールドはMSB-first。

CRC値の格納は指定されたByteOrderに従う。

CRC-16：

```text
ByteOrder = Big-endian
```

CRC-32：

```text
ByteOrder = Big-endian
```

したがってCRC値の上位byteから順番に格納する。

---

# 25. CRC計算時のbit列

CRC対象がbyte境界に一致しない場合は、末尾に0bitを追加してbyte化する。

この0bitはQR構造上のPaddingと同一である。

つまり、

```text
[CRC対象bit列][0-padding]
```

をbyte列としてCRC計算へ渡す。

別途CRC専用のpaddingを追加することはない。

ただし後続Frameでは、現在QRのPaddingを含めて現在QRのCRC対象byte列を確定した後、その後ろへFirst QRのFrame CRC 16bitをBig-endianで連結する。

First CRCを追加するために現在QRのPayloadやPaddingを再配置しない。

bitstreamからbyte列への変換は通常の8bit区切りによる詰め方を使用する。

---

# 26. Overall Checksum

Final QRにはOverall Checksumが存在する。

Overall Checksumは32bit。

アルゴリズム：

```text
CRC-32/ISO-HDLC
```

パラメータ：

```text
Width     = 32
Poly      = 0x04C11DB7
Init      = 0xFFFFFFFF
RefIn     = true
RefOut    = true
XorOut    = 0xFFFFFFFF
Check     = 0xCBF43926
ByteOrder = Big-endian
```

Overall CRCの入力が0bitである場合も、特殊扱いせず通常のCRC-32/ISO-HDLCとして計算する。

---

# 27. Overall CRCの対象

Overall CRCは各FrameのHeaderやFrame CRCを対象としない。

全FrameのPayloadをFrame Number順に並べて連結したものを対象とする。

```text
Payload 0
+
Payload 1
+
...
+
Payload N-1
```

これをCRC-32/ISO-HDLCで計算する。

Overall CRCの計算に使用するPayloadは、通信プロトコル上のPayloadデータとして扱われる `Uint8Array` / byte列を基準とする。

String modeであっても、Frame CRCやOverall CRCの検証においては、まずPayloadをbyte列として扱い、文字列そのものを直接CRC計算対象にしない。

String modeのASCII 7bit packingについても、文字列へ復元してからCRCを計算するのではなく、通信上のPayload byte列を対象とする。

Overall CRCの計算において、入力が0bitとなる場合も通常のCRC-32計算を行う。

---

# 28. Final QRと通信終了の違い

Final QRを受信したことと、通信が終了したことは別である。

```text
Frame Number = Total QR Count - 1
```

であるQRはFinal QR。

しかし、他のFrameがまだ欠落している場合は通信終了ではない。

Missing Frameの判定はFinal QR受信を待つものではなく、現在のFrame保存状況から常に判定する。

通信終了条件は、

```text
Frame 0 ～ N-1 の全Frameが揃う
```

ことである。

その時点でPayloadをFrame Number順に連結し、Overall CRCを検証する。

---

# 29. Overall CRCによる通信完了判定

全Frameが揃ったら、

```text
Payload 0
Payload 1
...
Payload N-1
```

を順番に連結する。

その結果に対してCRC-32/ISO-HDLCを計算する。

Final QRに含まれるOverall Checksumと比較する。

```text
一致
→ 通信成功

不一致
→ 通信成功ではない
→ 深刻なエラー
```

Overall CRCは「Final QRを受信した時点」ではなく、「全Frameが揃って終了条件になった時点」で検証する。

Overall CRCが不一致の場合、通信を正常完了とは扱わず、深刻なエラーとして通信を終了する。

---

# 30. 送信処理

送信開始時：

1. Data APIが入力データを解析
2. Data Typeを決定
3. 必要なPayload bitstreamを生成
4. 必要なFrame数を決定
5. Frame Numberを割り当てる
6. First QRを生成
7. Intermediate QRを生成
8. Final QRを生成
9. 各FrameのCRCを生成
10. Final QRのOverall CRCを生成
11. Browser RuntimeへQRモジュール情報を渡す

Frame Numberは0-basedであるため、最初のFrameには `0` を割り当てる。

送信中は、

```text
0 → 1 → ... → N-1
```

を繰り返す。

```text
N-1 → 0
```

と戻った後も送信を継続する。

String modeでは、String Mode bitを通信全体のPayloadの先頭に一度だけ付加してからPayload bitstreamを生成する。

その後、生成されたbitstreamをFrame単位にbit分割する。

---

# 31. 送信停止

送信は自動停止しない。

ユーザーまたはAPIから明示的に停止する。

```text
stop()
```

等のAPIによって停止する。

停止時点が、

* First
* Intermediate
* Final
* 周回途中

のどこであるかは問わない。

送信中に `start()` が再度呼び出された場合、現在の送信状態に関係なく、そのStart要求は無視する。

すでに開始済みの通信を二重に開始しない。

Stop時にはQR Canvasをクリアする。

---

# 32. 受信開始前

First QRが読み込まれる前は、正式な通信は開始されていない。

後続QRと思われるデータを受信した場合でも、First QRが存在しない状態では正式な解析・CRC検証を行わない。

ただし、受信したQRデータそのものは一時保存できる。

---

# 33. First QR到着前の一時保存

First QR到着前に受信したQRデータは一時保存する。

保存形式は画像ではなく、

```text
Uint8Array
```

とする。

一時保存数には設定可能な上限を設ける。

上限到達後は追加のQRデータを無視する。

無制限にキューを増加させない。

同じFrame Numberのデータが一時保存領域に既に存在する場合、その重複データは無視する。

First QR到着前の一時保存データは、通信の正式なFrame処理結果ではない。

そのため、これらのデータを仮読み込み・keepとして保持しているだけの場合、その存在はCRC連続エラー回数の成功・失敗カウントに影響しない。

---

# 34. First QR前のCRC検証

First QRを受信する前は、後続FrameのCRC検証を行わない。

後続FrameのCRCにはFirst QRのFrame CRCが必要だからである。

したがって、

```text
First QR
    ↓
First CRC確定
    ↓
後続Frame CRC検証可能
```

という順序になる。

---

# 35. First QR受信後の一時保存データ処理

First QRが正常に処理された後は、通信情報を確立する。

その後の新規Camera QRデータを優先して処理する。

以前に一時保存していたQRデータは、処理能力・容量・タイミング等に余裕がある場合に順次処理する。

基本的にはキューの先頭から処理する。

Cameraから新しく受信したQRを処理することが優先される。

一時保存データの解析は、余力がある場合に1件ずつ行うことを基本とする。

ただし、一度に処理する個数は設定可能とし、具体的な値は実装・ユーザー設定によって決定する。

不要になった一時保存データの判定にはFrame Numberの一致を使用する。

新しいCamera QRの処理によって一時保存データが不要になった場合、その一時保存データは削除する。

一時保存データは正式な新規入力によるFrame処理とは区別する。

---

# 36. Frameの重複受信

正常に処理済みのFrameを再受信した場合、毎回完全なパースやCRC検証を行う必要はない。

既処理Frameについては、まず、

* Frame Number
* Payload Length

等の必要最小限の情報のみ確認する。

同一Frame Numberで、既処理時と同じLengthである場合は、既処理データとして無視する。

これはCPUの無駄な消費を防ぐためである。

Frame NumberとPayload Lengthが一致した時点でSkipを確定し、それ以上のCRC検証等を行わない。

SkipはCRC成功でもCRC失敗でもない。

---

# 37. 既処理Frameの内容変更

既に処理済みのFrame Numberであるにもかかわらず、Payload Length等が以前と異なる場合は、単純に無視しない。

そのFrameについて通常のQR変更検出・整合性確認と同じ処理を行う。

処理順序は、

```text
Frame Number
    ↓
Payload Length
    ↓
Frame内容の整合性確認
```

とする。

既処理FrameについてPayload Lengthが以前と異なる場合、First CRCが一致しているかどうかに関係なく、別通信データへ切り替わった可能性を考慮する。

新しいFrameについてCRCを含む必要な整合性チェックを行い、検証の結果、

```text
完全に正常なデータ
```

である場合は、以前保存していたFrameデータを新しいデータへ交換する。

整合性チェックが不正である場合は、以前保存していたFrameを維持する。

このような事象は警告対象とし、APIの、

```text
onXXXXWarn
```

等のWarning通知機構から通知する。

この基本処理はFirst Frameを含めて共通とする。

First Frameについては、これに加えてFirst CRC変更時の通信基準更新処理を行う。

---

# 38. First QRの再受信

First QRについても、既に確立済みの通信情報が存在する場合は、不要な完全解析を繰り返さない。

必要最小限の情報を確認する。

First QRのFrame Numberは常に `0` である。

First QRの内容に差異がある場合は、通常の既処理Frame変更処理として必要な整合性確認を行う。

特にFirst QRのFrame CRCを比較する。

First QRには、First CRC変更による通信基準更新という追加の処理が存在する。

---

# 39. First CRCが変更された場合

新しく受信したFirst QRのFrame CRCが、現在通信に使用しているFirst QRのFrame CRCと異なる場合は、現在保存しているFrame 1以降のデータを破棄する。

0-based Frame NumberではFirst QRがFrame 0であるため、破棄対象は、

```text
Frame 1
Frame 2
...
Frame N-1
```

となる。

理由は、後続FrameのCRC計算に使用するFirst CRCが変わるためである。

処理：

```text
新しいFirst QR
    ↓
First CRC比較
    ↓
CRCが異なる
    ↓
Frame 1以降の保存データ破棄
    ↓
新しいFirst QRを通信基準として使用
```

これは通常の「既処理Frameの内容変更」とは別種類の異常・警告として扱う。

APIでは別種類のWarningとして通知する。

なお、First CRCが一致していても、Frame NumberやPayload Length等の変更条件が存在する場合は、通常のFrame変更処理を適用する。

---

# 40. Missing Frame

Frameは必ず0からN-1まで揃う必要がある。

Missing FrameはFinal QRの受信を待たず、**常に現在の保存状況から判定する**。

例えば、

```text
0 → 1 → 3 → 4
```

と受信した場合、Frame 2が欠落している。

この場合は通信完了とはならない。

送信側は、

```text
0 → 1 → 2 → 3 → 4 → 0 → ...
```

とループしているため、Frame 2が再び送信されるのを待つ。

Final QRを先に受信した場合でも、欠落Frameが存在する限り通信は終了しない。

---

# 41. Out-of-range Frame Number

First QRから取得したTotal QR Countに対して、

```text
Frame Number >= Total QR Count
```

となるFrameは無効。

Frame Numberはbitstream上のunsigned値として扱うため、通常の構文上は負値そのものは存在しない。

実際には、

```text
Frame Number >= Total QR Count
```

となるFrameを範囲外として扱い、無視する。

Frame Number `0` は有効なFrame Numberである。

FrameBitsによって表現可能ではあるがTotal QR Countの範囲を超える余剰bitパターンも、この規則によって無視する。

---

# 42. CRCエラー

CRC不一致は、そのQRのデータを有効なFrameとして処理しない。

CRCエラーが発生した場合、そのFrameは破棄・再取得対象とする。

送信側は同じFrameをループ中に再送するため、再受信を待つ。

単発のCRCエラーは、それだけで直ちに通信終了とはしない。

CRC不一致は通常の通信エラーとして扱い、設定された連続エラー閾値に達するまでは通信を継続する。

---

# 43. CRCエラー回数

CRCエラー回数は、**連続CRCエラー回数**として管理する。

有効なCRCを持つFrameを受信した場合、連続エラー状態をリセットする。

既に正常処理済みのFrameを再受信し、既処理FrameとしてSkipした場合は、

* 成功として数えない
* 失敗として数えない
* 連続CRCエラー回数を変更しない

。

つまりSkipはCRC成功・失敗のどちらでもない。

```text
CRC Error
→ 連続エラー +1

CRC Success
→ 連続エラーをリセット

Already Processed / Skip
→ 何も変更しない
```

CRC連続エラー閾値は設定可能とする。

デフォルト値は、

```text
16回
```

とする。

設定値は、

```text
0以上
```

でなければならない。

```text
0
```

は無制限を意味する。

```text
0未満
```

は設定エラーとする。

CRC連続エラー回数として数えるのは、**新規入力として受信・処理したQRについて発生したCRC成功・失敗**である。

First QR到着前の仮読み込み・keepとして一時保存しているデータについては、古い別通信のQRである可能性があるため、CRC連続エラー回数のカウント対象としない。

設定された連続CRCエラー回数の閾値に到達した場合、通信を**深刻なエラーとして終了する**。

このエラー終了は通常のCRCエラーによる一時的な再取得とは異なり、通信を継続できない状態として扱う。

---

# 44. CRC検証順序

QRを処理する際、CRCによってデータの整合性を確認できる場合は、意味的な処理を進める前にCRCを確認する。

ただしCRC位置を決定するために必要な構文解析は先に行う。

つまり、

```text
構文解析
    ↓
CRC位置決定
    ↓
CRC検証
    ↓
意味的妥当性検証
    ↓
Frame処理
```

という考え方である。

構文解析自体に失敗してCRC位置を確定できない場合は、CRC不一致として扱わず、構文解析エラーとして扱う。

---

# 45. Invalid QR

以下のようなQRは無効またはエラーとして扱う。

## Version 0

エラー。

## 未対応Version

可能な範囲で解析を試みる。

構造が現在のライブラリで理解できない場合はエラー。

構造を理解でき、通信を継続できる場合はWarningとして扱う。

## Undefined Data Type

```text
10
11
```

は現行仕様ではエラー。

将来拡張用に予約されている。

## Invalid Total QR Count

```text
0
```

など通信情報を確立できない値はエラー。

## Invalid Frame Number

範囲外の場合は無視。

`0` は有効なFrame Numberであるため、Invalid Frame Numberとして扱わない。

## Invalid Payload Length

Payload Lengthの表現が、

* 冗長
* 構造上不正
* Checksum領域まで到達する
* Checksumを確保できない
* その他構造と矛盾する

場合は無効。

Payload Lengthの異常によりChecksum位置そのものを決定できない場合は、CRCエラーではなく構文解析エラーとして扱う。

Payload Length `0` 自体は有効である。

## Invalid Padding

Paddingが0以外の場合は無効。

---

# 46. Payload Lengthによる構造解析

Payload LengthはChecksum位置を決定するために使用する。

したがって受信側は前方から順番に、

```text
Start
→ Version等
→ Total QR Count
→ Frame Number
→ Data Type
→ Payload Length
→ Payload
→ Padding
→ Frame Checksum
→ Overall Checksum（Finalのみ）
```

と解析する。

単純にQRデータ末尾からCRCを決め打ちすることはしない。

String modeの場合も、Payload LengthによってまずPayloadのbit範囲を決定し、その内部の先頭1bitをString Modeとして解釈する。

String Modeの先頭1bitは通信全体のPayloadの先頭にのみ存在し、後続Frameでは再度現れない。

### 46.1 Frame容量とPayload分割

Data APIがFrameを生成する際、1つのFrameに格納できるPayloadの量は、Frame全体のbit数によって制限される。

Frame全体のbit数には、以下を含む。

```text
Start
→ Version等 (Firstのみ)
→ Total QR Count (Firstのみ)
→ Frame Number
→ Data Type
→ Payload Length
→ Payload
→ Padding
→ Frame Checksum
→ Overall Checksum（Finalのみ）
```

したがって、Frameに格納するPayload bit数は、単純にFrame全体の最大bit数から固定長のHeaderおよびChecksumを差し引いて決定するものではない。

特に、以下の要素によって実際に格納可能なPayload bit数が変化する。

* Total QR CountによるFrameBitsの変化
* Payload Lengthのbit長
* Paddingのbit数
* First / Intermediate / FinalによるFrame構造の違い
* Finalにのみ存在するOverall Checksum

そのため、Data APIはFrameを生成する際、実際に生成されるFrameの構造を考慮して、指定されたFrame全体の最大bit数を超えない範囲でPayloadを分割する。

Frame全体の最大bit数を `MaxFrameBits` とした場合、各Frameについて、

```text
Frameの実bit数 <= MaxFrameBits
```

を満たさなければならない。

First、Intermediate、Finalの各Frameでは構造が異なるため、それぞれでPayloadとして格納可能なbit数も異なってよい。

Payloadは各Frameに必ず同じbit数ずつ格納する必要はない。

また、Total QR CountはFrameBitsの決定に使用されるため、Total QR Countの決定とPayload分割は相互に関係する。

Data APIは、対象Payload全体を格納できるTotal QR Countを決定したうえで、そのTotal QR Countから確定するFrameBitsを使用して各Frameの容量を決定する。

Total QR Countを決定する際は、必要以上にFrame数を増やさず、Payload全体を格納可能な最小のTotal QR Countを使用する。

なお、QR VersionやError Correction Levelから `MaxFrameBits` を算出する具体的な方法については、別途定義する。

---

# 47. Data APIによるQRデータ生成

送信側のData APIはQRプロトコルに従ったbitstreamを生成する。

生成されたQRデータはQRモジュール情報へ変換される。

モジュール情報は黒/白を表すbinary dataとする。

例えば、

```text
[1, 1, 0, 0, ...]
```

のような形式。

Data APIはQRのProtocol DataおよびModule Informationを生成する。

Browser Runtime APIは、そのモジュール情報を実際の画面へ描画する。

String modeの場合、Data APIはStringを指定されたString Modeへ変換し、

```text
[Mode 1bit][String Data]
```

のPayload bitstreamを生成した上でFrame分割を行う。

ASCII Modeでは送信前にASCII範囲を確認する。

```text
0x00 ～ 0x7F
```

以外の値をASCII Modeで送信しようとした場合は送信側でエラーとする。

UTF-8 Modeでは、文字コードのUnicode上の存在性を検証する処理は行わない。

### 47.1 Frame分割時の容量計算

Data APIは入力データをPayloadへ変換した後、PayloadをFrameへ分割する。

Frameへの分割では、46.1で定義するFrame全体の最大bit数を基準として容量を計算する。

各Frameについて、Frameを構成するすべてのフィールド、Payload、Padding、Frame Checksum、およびFinalの場合はOverall Checksumを含めたFrame全体のbit数が、指定された最大bit数を超えてはならない。

First Frame、Intermediate Frame、Final FrameではFrame構造が異なるため、それぞれ異なるPayload bit数を格納してよい。

Payloadの分割は元のPayload bitstreamに対して行い、Frame境界によってPayloadのbit順や内容を変更してはならない。

Stringの場合も同様に、String Modeを含む完成後のPayload bitstreamをFrame境界で分割する。String ModeをFrameごとに追加してはならない。

Frame分割後の各Frameは、既存のFrame構造およびChecksum規則に従って生成する。

---

# 48. Browser RuntimeによるQR表示

Browser Runtime APIはData APIが生成したモジュール情報を受け取り、

* Canvas
* DOM
* その他対応する描画手段

によって表示する。

Browser Runtime API自身が通信プロトコルのPayloadやChecksumを生成することはない。

Stop時にはQR表示Canvasをクリアする。

---

# 49. Camera受信

受信時はBrowser Runtime APIがCameraおよびMediaStreamを制御する。

Cameraから取得した画像をData API側へ渡す。

Camera / QR Decoderから取得した生データは `QRrawData` として扱う。

Data API側ではQR画像からQRデータを取得し、その後TypeScript側でプロトコル解析およびFrame結合を行う。

プロトコルとして解析されたbitstreamを `QRdata` とする。

画像処理・QRデコードの一部または全部についてRust/WASMを利用する可能性がある。

Rust/WASMにどこまで処理を移すかは、実装・性能検証後に確定する。

---

# 50. Worker

Workerが利用可能かつ有効化されている場合はWorkerを利用する。

OffscreenCanvas等、Worker側で利用可能なブラウザ機能も活用する。

Workerを利用できない場合、または設定によって無効化されている場合はMain ThreadへFallbackする。

---

# 51. Worker / Main Threadの共通化

Worker用とMain Thread用で共通ロジックを二重実装しない。

共通のRuntime abstraction / wrapperを利用する。

理想的には同一JSファイルを、

```ts
if (isWorkerContext()) {
    runWorker();
} else {
    runMain();
}
```

のようなRuntime判定によってWorker / Main Thread双方で利用できる構成とする。

# 58. 通信状態

概念上、受信側には少なくとも以下の状態が存在する。

```text
Idle
  ↓
Waiting for First
  ↓
First Established
  ↓
Receiving
  ↓
Waiting Missing Frames
  ↓
Overall CRC Verification
  ↓
Completed
```

エラー時にはError状態へ遷移する。

ユーザーによる停止・キャンセルも可能とする。

First QR到着前に後続QRが存在しても、通信状態としては正式な通信開始とはみなさない。

Start後に再度Startが呼ばれた場合は、現在の状態に関係なく無視する。

Stop後にStartした場合は、新しい通信として最初から開始する。

Error停止後にStartした場合も、新しい通信として最初から開始する。

---

# 59. First CRCを利用した通信単位

First QRのFrame CRCを後続Frame CRCに含めることで、通信ごとの識別情報を別途追加しない。

通信A：

```text
First CRC = A
```

通信B：

```text
First CRC = B
```

の場合、それぞれの後続Frameは異なるCRC入力を持つ。

したがって、古い通信のFrameを新しい通信へ誤って混在させることを検出できる。

ただし、Frame NumberとPayload Length等の変更検出はFirst CRCの一致だけに依存しない。

特に同一Frame NumberでPayload Lengthが異なる場合は、First CRCが一致していても別通信データへ切り替わった可能性を考慮し、通常のFrame変更検出・整合性確認を行う。

---

# 60. First CRC変更時のFrame破棄

First CRCが変わった場合は、

```text
Frame 1
Frame 2
...
Frame N-1
```

の保持データを破棄する。

Frame 0に相当するFirst QRは新しい通信基準として更新する。

このイベントは通常のFrame更新Warningとは別に通知する。

---

# 61. Warning

通信を即座にエラー終了させるほどではないが、通常とは異なる状態についてWarning通知を行う。

例：

* 既処理Frameの内容変更
* 正常な新データによる既存Frame交換
* First CRC変更による後続Frame破棄
* 未知Versionだが構造を理解でき、通信を継続可能な場合
* その他、実装上定義される警告

Warningの具体的なAPI名は実装時に確定する。

Warningは通信進行そのものを停止させない。

---

# 62. Error

通信を継続できない状態ではErrorとして扱う。

例：

* 不正なFormat Version
* 未定義Data Type
* 不正なTotal QR Count
* 構造解析不能
* ASCII範囲外のデータをASCII Modeで送信しようとした場合
* String decode不能
* CRC連続エラーが設定閾値を超過
* Final QRを含む全Frame取得後のOverall CRC不一致
* その他プロトコル上継続不能な状態

Errorは通信継続への影響によって分類する。

### 通常Error

異常または不整合が存在するが、該当データを破棄・再取得するなどして本進行を継続できる場合。

### Critical Error / 深刻なエラー

通信そのものを継続できない場合。

特に以下は**深刻なエラー**として扱う。

* First QRの処理における通信確立不能なエラー
* CRC連続エラーが設定された閾値に到達した場合
* Overall CRC不一致
* その他、通信継続不能と定義されたエラー

深刻なエラーが発生した場合は通信をError停止状態へ移行する。

一方、単発のFrame CRC不一致は、連続CRCエラー数の増加対象ではあるが、それだけで深刻なエラーとして即座に停止するものではない。

構造を理解できず通信を継続できない場合はErrorとする。

# 65. プロトコル上の重要な順序

QR受信時の基本的な順序は以下とする。

```text
1. QRデータ取得
2. 構文解析
3. 必要な位置情報の確定
4. CRC検証
5. 基本的な値の妥当性確認
6. Frame状態確認
7. Frame保存 / 更新 / Skip
8. Missing / 完了判定
9. Overall CRC検証
10. 必要に応じてString復元
```

ただし、CRC計算そのものに必要な構造解析はCRC検証より前に行う。

CRC位置まで到達できない構文エラーは、CRCエラーとして扱わない。

Frame NumberとPayload Lengthが一致する既処理Frameは、不要なCRC検証を行わずSkipできる。

---

# 66. 全Frameの保存

受信した正常FrameはFrame Numberをキーとして管理する。

```text
Frame 0
Frame 1
...
Frame N-1
```

の順序で最終的なPayloadを再構築する。

受信順序そのものは最終データの順序を決定しない。

例えば、

```text
0 → 2 → 1 → 4 → 3
```

の順で受信しても、

```text
0 → 1 → 2 → 3 → 4
```

の順にPayloadを結合する。

同一Frame Numberに対して正常な新Frameが到着した場合、必要な整合性確認後に既存Frameを交換できる。

---

# 67. 受信データの一貫性

同一Frame Numberに対して複数のデータが存在する場合、正常に検証された最新のデータへ交換できる。

ただし、既処理データと異なる内容が検出された場合はWarningを通知する。

CRC不一致データは有効なデータとして交換しない。

Frame Number `0` はFirst QRに対応するため、First CRC変更時の通信基準更新処理と通常のFrame交換処理を区別する。

Frame NumberとPayload Lengthが一致する既処理Frameは、内容確認を省略してSkipする。

Payload Lengthが以前と異なる場合は、First CRCの一致・不一致に関係なく通常の変更検出・整合性確認を行う。

---

# 68. Communication Completion

通信成功の条件は、

1. First QRを正常に取得
2. Total QR Countを確定
3. Frame 0～N-1をすべて取得
4. 各Frameが有効
5. PayloadをFrame Number順に結合
6. Overall CRCが一致

することである。

すべてを満たした場合のみ通信成功とする。

成功後、受信側は自動的に通信を停止する。

成功後の再Startは、新規通信開始として扱う。

---

# 69. SenderとReceiverの非対称性

送信側は受信側の状態を知らない。

そのため、

```text
Sender
0 → 1 → ... → N-1 → 0 → ...
```

を継続する。

Receiverは必要なFrameを受信し終え、Overall CRCを確認した時点で停止する。

このため、送信側と受信側の停止条件は異なる。

Senderは全Frameを一周しても自動停止しない。

Receiverは通信成功後に自動停止する。

---

# 70. CRCの責務

Frame CRC：

```text
各QR単位の整合性確認
```

First CRCを後続FrameのCRCへ含めることで、

```text
同一通信への所属確認
```

も兼ねる。

Overall CRC：

```text
全Payloadを結合した最終データの整合性確認
```

を担当する。

したがって、

```text
Frame CRC
    ↓
個々のQR / 通信単位の整合性

Overall CRC
    ↓
完成した最終データ全体の整合性
```

という役割分担になる。

---

# 71. CRCの二段階構造

通信全体では、

```text
First QR
  ↓
First Frame CRC
  ↓
Frame 1 CRC ← First CRC
  ↓
Frame 2 CRC ← First CRC
  ↓
...
  ↓
Final Frame CRC ← First CRC
  ↓
全Frame取得
  ↓
Payload連結
  ↓
Overall CRC
```

という構造になる。

Frame Numberは0-basedであるため、First QRはFrame 0である。

# 72. 現時点で確定している設計原則

1. 通信は一方向である。
2. ライブラリは送信・受信双方を提供する。
3. 内部データは `Uint8Array` を基本とする。
4. APIはData / Transport / Browser Runtimeの3層に分離する。
5. Data APIはブラウザに依存しない。
6. Browser Runtime APIがCamera、DOM、Canvas、Worker等を扱う。
7. WorkerとMain Threadで共通ロジックを重複実装しない。
8. Workerが利用可能なら利用し、不可ならMain ThreadへFallbackする。
9. QRは0～N-1のFrameに分割される。
10. Senderは0～N-1を無限ループする。
11. Senderは自動停止しない。
12. First QRはStart Bit = 1かつFrame Number = 0で識別する。
13. Intermediate / FinalはFrame Numberで判定する。
14. Frame Number = Total QR Count - 1がFinalである。
15. Total QR Count = 1ではFrame 0がFirstかつFinalとなる。
16. ビットストリーム上の通常フィールドはMSB-firstである。
17. Varint内部の6bit DataだけLSB-firstである。
18. Uint8Arrayのbyte順はindex順である。
19. Uint8Array各byteのbit順はMSB-firstである。
20. フィールド間でbyte alignmentを行わない。
21. Payload Lengthはbit数を表す。
22. Payload Lengthは各FrameのPayload bit数を表す。
23. Payload Length 0を許可する。
24. Paddingは末尾の0bitである。
25. PaddingはCRC計算時のbyte化にも同じものを使用する。
26. Paddingは0以外を許可しない。
27. PayloadのFrame分割はbit単位で行う。
28. Frame境界でbyte境界や文字境界を維持する必要はない。
29. Frame CRCはCRC-16/CCITT-FALSEである。
30. Frame CRCはChecksum以前の全bitを対象とする。
31. Frame CRCの対象には現在FrameのPaddingも含む。
32. First QR以外のFrame CRCにはFirst QR CRCを追加する。
33. First QR自身には前提CRCを追加しない。
34. 後続Frameでは現在FrameのCRC対象byte列の後ろにFirst CRCを連結する。
35. Overall CRCはCRC-32/ISO-HDLCである。
36. Overall CRCは全PayloadをFrame Number順に連結したものを対象とする。
37. Overall CRCの入力が0bitでも通常通りCRCを計算する。
38. Final QR受信と通信終了は同一ではない。
39. Missing FrameはFinal受信を待たず常に現在の保存状況から判定する。
40. 全Frameが揃った時点でOverall CRCを検証する。
41. Overall CRC一致時のみ通信成功とする。
42. First QR到着前の後続QRは正式には処理しない。
43. First QR到着前のQRは制限付きで一時保存できる。
44. 一時保存はUint8Arrayで行う。
45. 一時保存数には上限を設ける。
46. First QR到着前は後続FrameのCRC検証を行わない。
47. First QR確立後はCameraからの新規QRを優先する。
48. 仮読み込み・keepデータはCRC連続エラー回数に影響しない。
49. 既処理Frameは不要な完全解析を行わない。
50. Frame NumberとPayload Lengthが一致する既処理FrameはSkipする。
51. 既処理FrameのSkipはCRC成功・失敗のどちらにも数えない。
52. CRCエラー回数は連続CRCエラー回数である。
53. デフォルトCRC連続エラー閾値は16回である。
54. CRC連続エラー閾値0は無制限を意味する。
55. CRC連続エラー閾値0未満は設定エラーである。
56. 有効CRCで連続エラー状態をリセットする。
57. 既処理Skipでは連続エラー状態を変更しない。
58. 同一Frame NumberでもLength等が異なる場合は検証する。
59. First CRCが同じでもLengthが異なる場合は通常の変更検出を行う。
60. 正常な新データなら既存Frameを交換する。
61. CRC等の整合性確認に失敗した新Frameでは既存Frameを維持する。
62. Frame交換はWarning対象とする。
63. First CRCが変更された場合はFrame 1以降を破棄する。
64. First CRC変更は別種類のWarningとする。
65. Missing FrameはSenderのループによる再送を待つ。
66. Out-of-range Frame Numberは無視する。
67. Frame Number 0は予約値ではなく正規のFrame Numberである。
68. 構文解析と意味的妥当性検証を分離する。
69. CRC検証には構文解析が必要である。
70. CRC位置を確定できない構文エラーはCRCエラーとして扱わない。
71. CRC検証後に意味的なFrame処理を行う。
72. Data APIの通信結果にはtype情報を付加する。
73. Data APIは通信状態・Frame保存状態を保持しない。
74. Frame Numberの解析・データ検証はData APIが担当する。
75. Frame保持・上書き・Skip等の状態管理はTransport APIが担当する。
76. CRC連続エラー回数はTransport APIが管理する。
77. Overall CRCの検証・分類はData APIが担当する。
78. Warning / Error callbackはTransport APIが担当する。
79. QR Module DataはData APIが生成する。
80. Browser Runtime APIはModule Dataを描画する。
81. Camera画像はBrowser RuntimeからData APIへ渡す。
82. `QRrawData` はQR Decoderから得た生データを表す。
83. `QRdata` はプロトコルbitstreamを表す。
84. Payloadは本文・本データを表す。
85. CRC inputはQRdataのCRC対象部分を表し、Overall CRCを除外する。

87. Rust/WASMの責務範囲は性能検証後に確定する。

89. デフォルトQR Versionは5。

96. Start後のStartは状態に関係なく無視する。
97. StopはComplete以前の任意の状態から実行可能とする。
98. Stop時にはQR Canvasをクリアする。
99. Stop後のStartは新規通信としてFrame 0から開始する。
100. 深刻なエラー停止後のStartも新規通信としてFrame 0から開始する。
101. First QR関連の深刻なエラーはError停止とする。
102. CRC連続エラー閾値到達は深刻なエラーとする。

104. 単発のCRCエラーは直ちに通信終了させない。

127. UTF-8 byte境界・文字境界でFrame分割する必要はない。
128. Frame再結合後に初めてString全体を復元する。

* QR Decode性能
* Rust/WASMの分担

など、実装・実機検証によって決定すべき事項はプロトコル仕様から分離する。

一方、

* bit order
* byte order
* field order
* Frame Number
* CRC
* Payload Length
* padding
* First CRCによる通信識別
* Final判定
* Overall CRC
* Frame再受信処理
* Start / Stop状態
* String modeのPayload形式

など、送受信実装間で一致していなければ通信そのものが成立しない事項はプロトコル仕様として明確に固定する。

---

# 75. Start / Stop / Error停止のライフサイクル

通信の開始・停止について、以下を正式な状態仕様とする。

## 75.1 Start

Start操作によって通信を開始する。

Start後は、通信状態に応じた通常の送信または受信処理を行う。

Start後に再度Startが呼び出された場合、そのStart操作は無視する。

これは、

* Waiting for First
* First Established
* Receiving
* Waiting Missing Frames
* Overall CRC Verification
* その他のComplete以前の状態

を問わない。

既存通信を途中から再初期化したり、二重に開始したりしない。

CompleteまたはStop/Errorによって通信が終了した後のStartは、新規通信開始として扱う。

---

## 75.2 Stop

Stopは、通信がCompleteになる前であれば、任意の状態から実行できる。

例えば、

* First QR待機中
* First QR確立後
* Frame受信中
* Missing Frame待機中
* Overall CRC Verification中
* その他の通信途中

のいずれからでもStopできる。

Stopによって現在の通信を終了する。

Stop時には現在表示しているQR Canvasをクリアする。

---

## 75.3 Stop後の再Start

Stop後にStartされた場合、以前の通信状態を引き継がない。

新しい通信として最初から開始する。

したがってFrame Numberは再び、

```text
0
```

から開始する。

受信側についても、以前の通信に属するFrame保存状態を新しい通信へ引き継がない。

受信側は、

```text
Waiting for First
```

から開始する。

---

## 75.4 Error停止後の再Start

深刻なエラーによって通信が停止した場合も、次のStartは新しい通信として扱う。

以前の通信状態を引き継がない。

Frame Numberは再び、

```text
0
```

から開始する。

特に、

* First QR関連の深刻なエラー
* CRC連続エラー閾値到達
* Overall CRC不一致

などによってError停止した場合も同様である。

Error停止時には現在の通信に属する保持データを破棄する。

次のStartでは旧通信のFrame、First情報、CRCエラー状態等を利用しない。

---

# 76. String mode

String modeは、文字列データを通信するためのData Typeである。

旧仕様で使用していた `utf8string` という名称は使用せず、正式名称を `string` とする。

String modeでは、通信Payloadを以下の構成で保持する。

```text
[1bit String Mode]
[String Data]
```

先頭1bitが文字列データの符号化方式を表す。

```text
0 = ASCII Mode
1 = UTF-8 Mode
```

この1bitはString modeのPayloadの一部である。

通信全体のPayloadの先頭に一度だけ存在する。

Frame分割後の2Frame目以降にはこのMode bitを再掲しない。

---

## 76.1 ASCII Mode

ASCII Modeでは、String DataをASCII文字として扱う。

ASCII値として使用可能な範囲は、

```text
0x00 ～ 0x7F
```

である。

ASCII範囲外の値をASCII Modeとして送信しようとした場合、送信側でエラーとする。

各文字を7bitのASCII値として表現し、それらを7bit単位で連続してPayloadへ詰める。

例えばASCII文字が、

```text
A
B
C
```

の場合、それぞれのASCII値を7bitで表現し、

```text
0100001
0100010
0100011
```

のように連続して配置する。

ASCII Modeでは8bit byte境界ごとに文字を格納するのではなく、**7bit packing**を行う。

そのため、ASCII文字列全体のString Data bit長は、

```text
7 × 文字数
```

となる。

String Payload全体ではMode bitが先頭に追加されるため、

```text
1 + (7 × 文字数)
```

がPayload全体のbit長となる。

その後、Frame全体のbitstreamがbyte境界に到達しない場合に、通常のFrame Paddingを末尾へ追加する。

ASCII Modeの7bit packingによるbit列と、Frame末尾のPaddingは別の概念である。

---

## 76.2 UTF-8 Mode

UTF-8 Modeでは、String DataをUTF-8 byte列として扱う。

各UTF-8 byteは8bit単位でPayloadへ格納する。

例えばUTF-8 byte列が、

```text
0x41 0x42 0x43
```

の場合、

```text
01000001 01000010 01000011
```

としてPayloadへ格納する。

UTF-8 ModeではASCII Modeのような7bit packingは行わない。

String Payload全体ではMode bitが先頭に追加されるため、

```text
1 + (8 × UTF-8 byte数)
```

がPayload全体のbit長となる。

UTF-8 Modeで使用されるbyte列について、現在のUnicode仕様に存在する文字かどうかを別途検証しない。

ただし、プロトコル上必要な8bit単位のデータ構造が成立しない場合はエラーとする。

---

## 76.3 String ModeとPayload Length

String modeのPayloadは、

```text
[1bit Mode][String Data]
```

で構成される。

したがってPayload Lengthは、Modeの1bitを含めた**Payload全体のbit長**を示す。

ASCII Modeの場合、

```text
Payload Length
=
1 + (7 × ASCII文字数)
```

を基本とする。

UTF-8 Modeの場合、

```text
Payload Length
=
1 + (8 × UTF-8 byte数)
```

を基本とする。

空文字列も許可する。

空文字列の場合でも、

```text
[1bit Mode]
```

は存在するため、String Payloadの長さは0ではなく1bitとなる。

Frame分割によってPayloadが複数Frameへ分かれる場合でも、通信全体として構成されたString PayloadのbitstreamをFrameへ分割する。

---

## 76.4 String modeのFrame分割

String modeのPayloadは、文字列として再分割するのではなく、生成されたPayload bitstreamを通信可能なFrameへ分割する。

したがって、ASCII ModeではFrame境界が7bit文字境界と一致するとは限らない。

同様に、UTF-8 ModeではFrame境界がUTF-8 byte境界・文字境界と一致するとは限らない。

Frame分割・再結合では、Payload bitstreamをそのまま順番通りに扱う。

通信全体のPayloadをFrame Number順に連結することで、元のString Payload bitstreamを復元する。

2Frame目以降にはString Mode bitを追加しない。

---

## 76.5 String modeの検証

String modeであっても、Frame CRCおよびOverall CRCの検証時には、文字列へ変換してから検証しない。

検証対象は通信プロトコル上のPayloadを表す `Uint8Array` / bitstreamとする。

つまり、

```text
QRrawData
 ↓
QRdata
 ↓
Payload
 ↓
Uint8Array / bitstream
 ↓
CRC
```

の順序で処理する。

文字列への変換は、通信全体の検証が成功し、最終的なData APIの結果を構築するときに行う。

UTF-8 Modeで文字コード上のUnicode妥当性を検証することはしない。

---

## 76.6 String modeの復元

全Frameが揃い、Overall CRCが成功した後、String modeの場合はPayloadを再構築する。

まず先頭1bitからString Modeを取得する。

```text
0
→ ASCII Mode

1
→ UTF-8 Mode
```

その後、String Modeに応じて残りのString Dataを復元する。

ASCII Modeでは7bit単位で文字を復元する。

UTF-8 Modeでは8bit単位のbyte列として復元し、Stringへ変換する。

ASCII Modeでは復元対象の7bit値が、

```text
0x00 ～ 0x7F
```

の範囲外となる場合はエラーとする。

UTF-8 Modeでは、単にUnicode上で存在しない文字コードであること自体はエラーとして扱わない。

ただし、Stringとしての復元処理そのものが失敗する場合はエラーとする。

---

# 77. Frame NumberとFrameBitsの確定定義

Frame Numberは0-basedである。

Total QR Countを `N` とした場合、

```text
有効Frame Number
=
0 ～ N-1
```

である。

FrameBitsは、

```text
FrameBits = max(1, ceil(log2(N)))
```

とする。

この定義ではFrame Number `0` が有効値であり、0を予約する必要はない。

例えば、

```text
N = 1
→ FrameBits = 1
→ Frame Number = 0

N = 2
→ FrameBits = 1
→ Frame Number = 0, 1

N = 3
→ FrameBits = 2
→ Frame Number = 0, 1, 2

N = 4
→ FrameBits = 2
→ Frame Number = 0, 1, 2, 3

N = 5
→ FrameBits = 3
→ Frame Number = 0 ～ 4
```

となる。

Frame Numberとして使用しないbitパターンが存在する場合、その値はTotal QR Countとの比較によって範囲外として扱う。

例えば、

```text
N = 5
FrameBits = 3
```

の場合、3bitでは、

```text
000 = 0
001 = 1
010 = 2
011 = 3
100 = 4
101 = 5
110 = 6
111 = 7
```

を表現できるが、

```text
5, 6, 7
```

は `N-1 = 4` を超えるため無効である。

これらの余剰bitパターンはエラーとして通信状態を停止させるのではなく、範囲外Frameとして無視する。

---

# 78. 深刻なエラーの扱い

通信上、単なる一時的な受信失敗と、通信を継続できない深刻なエラーを区別する。

## 通常のエラー

例えば単発のFrame CRC不一致は、通常の受信エラーとして扱う。

```text
CRC不一致
    ↓
Frame破棄
    ↓
同じFrameの再送を待つ
```

この時点では通信自体を停止しない。

---

## 深刻なエラー

以下は深刻なエラーとして扱う。

* First QRの通信確立に必要な重大なエラー
* CRC連続エラーが設定閾値に到達した場合
* 全Frame取得後のOverall CRC不一致
* その他、プロトコル上継続不能と定義されたエラー

深刻なエラーが発生した場合は、通信をError状態へ移行して停止する。

深刻なエラーによる停止時には、現在通信の保持データを破棄・リセットする。

---

## 深刻なエラー後の再Start

Error停止後にStartされた場合は、以前の通信を復旧するのではなく、新しい通信として開始する。

受信側は以前のFrame保存状態を利用しない。

送信側も以前の送信位置を利用しない。

新しい送信は、

```text
Frame 0
```

から始まる。

新しい受信は、

```text
Waiting for First
```

から開始する。

---

# 79. Start操作の重複

Startは通信開始操作である。

すでに通信が開始されている場合、Startを再度呼び出しても何も変更しない。

```text
Start
  ↓
通信開始

Start
  ↓
無視
```

これは通信状態に依存しない。

特に、

```text
Waiting for First
First Established
Receiving
Waiting Missing Frames
Overall CRC Verification
```

等の状態でStartを呼び出しても、現在の通信を再初期化しない。

CompleteまたはStop/Errorによって通信が終了した後のStartは、新規通信開始として扱う。

---

# 80. Stop操作

Stopは明示的な通信終了操作である。

Complete前であれば、どの通信途中状態からでも実行できる。

```text
任意の通信途中状態
        ↓
      stop()
        ↓
       Idle
```

Stopによって、

* 現在の通信状態
* 現在の送信位置
* 受信Frame状態
* 待機中の通信処理
* CRC連続エラー状態

を終了する。

受信側では現在保持している通信Frameを次の通信へ引き継がない。

送信側では現在のFrame位置を次の通信へ引き継がない。

また、Stop時にはQR表示Canvasをクリアする。

---

# 81. Stop / Error後の状態初期化

Stopまたは深刻なErrorによって通信が終了した場合、次回Startは新規通信として扱う。

したがって、

```text
旧通信
    ↓
Stop / Error
    ↓
状態破棄
    ↓
Start
    ↓
新通信
```

となる。

受信側では、

```text
旧通信のFrame 0～N-1
```

を新通信へ引き継がない。

送信側では、

```text
旧通信のFrame位置
```

を新通信へ引き継がない。

新しい送信はFrame 0から始まる。

新しい受信はWaiting for Firstから開始する。

First QR到着前の一時保存データも旧通信の状態として扱い、新しい通信へ引き継がない。

---

# 82. v6で確定した追加事項のまとめ

v6では、v5までのプロトコルを維持したうえで、以下を正式に確定した。

### Frame Number

```text
0 ～ N-1
```

の0-based。

`0`は予約値ではなく正規のFrame Number。

### First / Final

```text
First
→ Frame 0

Final
→ Frame N-1
```

`N = 1`の場合はFrame 0がFirstかつFinal。

### FrameBits

```text
FrameBits = max(1, ceil(log2(N)))
```

0-based Frame Numberにより、この式で0～N-1を表現する。

### String mode

正式名称：

```text
string
```

Payload：

```text
[1bit Mode][String Data]
```

Mode：

```text
0 = ASCII
1 = UTF-8
```

ASCII：

```text
7bit packing
```

UTF-8：

```text
8bit単位
```

ASCII範囲：

```text
0x00 ～ 0x7F
```

ASCII範囲外は送信側でエラーとする。

String Mode bitは通信全体のPayload先頭に一度だけ存在し、2Frame目以降では再掲しない。

### CRC

現在FrameのChecksum以前の全bitにはPaddingを含める。

後続Frameでは、

```text
Current Frame Data
+
First Frame CRC
```

の順でCRC-16へ入力する。

First CRCは現在Frameのbitstream内部へ挿入しない。

### Error

単発CRCエラーは通信継続。

CRC連続エラー閾値到達は深刻なエラー。

デフォルト閾値は16回。

`0`は無制限。

Overall CRC不一致も深刻なエラー。

仮読み込み・keepデータはCRC連続エラー回数に影響しない。

### Start

通信開始後のStartは状態に関係なく無視。

### Stop

Complete前なら任意の状態から実行可能。

Stop時にはQR Canvasをクリア。

### Restart

Stop後または深刻なError停止後のStartは新規通信。

送信はFrame 0から開始。

受信はWaiting for Firstから開始。

旧通信の状態は引き継がない。

### Payload

Payload Lengthはbit数。

Frame分割もbit単位。

byte境界・文字境界でFrameを分割する必要はない。

### Empty Data

空文字列を許可する。

空文字列ではString Mode bitのみを含む1bit Payloadとなる。

Uint8Array長0およびPayload Length 0も許可する。

# 83. v7で追加確定したデータ名称と責務

プロトコル処理上のデータを以下の名称で区別する。

## 83.1 QRrawData

QR Decoder等から取得した、生のQRデータ。

```text
Camera / QR Decoder
        ↓
QRrawData
```

QRrawDataは、プロトコル解析前の入力データである。

---

## 83.2 QRdata

QRrawDataからプロトコルとして扱えるbitstreamへ変換されたデータ。

```text
QRrawData
    ↓
QRdata
```

QRdata上でStart Bit、Version、Frame Number、Payload Length、Payload、Padding、Checksum等を解析する。

---

## 83.3 Payload

QRdataの構造中に存在する本文・本データ。

```text
[Header]
[Payload]
[Padding]
[Frame CRC]
```

のPayload部分である。

Payload LengthはこのPayloadのbit長を示す。

---

## 83.4 CRC input

CRC inputは、QRdataのうちFrame CRCを計算するために使用するデータである。

現在Frameについては、

```text
[Current Header]
[Current Payload]
[Current Padding]
```

を基本とする。

後続Frameでは、その後ろへ、

```text
[First Frame CRC]
```

をBig-endianの16bitとして連結する。

Overall CRCはFrame CRCとは別に、全FrameのPayloadを対象として計算する。

---

## 83.5 reconstructed payload

受信済みFrameをFrame Number順に連結して復元した通信全体のPayload。

```text
Frame 0 Payload
+
Frame 1 Payload
+
...
+
Frame N-1 Payload
```

によって生成する。

String modeの場合、このreconstructed payloadの先頭1bitをString Modeとして解釈し、残りをASCIIまたはUTF-8として復元する。

---

# 84. v7のError / Warning / Ignore分類

通信処理の異常は、通信継続への影響によって以下の3段階を基本とする。

## 84.1 Ignore

通信状態を変更する必要がなく、その入力を単純に処理対象から外すもの。

代表例：

* Out-of-range Frame Number
* Frame NumberとPayload Lengthが一致する既処理Frame
* First QR到着前に上限を超えて到着した一時保存対象外QR
* 不要になった一時保存QR

Ignoreは成功でも失敗でもない。

CRC連続エラー回数等の通信エラー状態にも影響を与えない。

---

## 84.2 Warning

異常または通常とは異なる状態だが、通信進行そのものには影響しないもの。

代表例：

* 既処理Frameの内容変更
* 正常な新FrameによるFrame置換
* First CRC変更による後続Frame破棄
* 構造を理解できる未知Version
* その他通信を継続可能な変更・異常

Warningは通信を停止しない。

---

## 84.3 Error

入力または通信状態に異常が存在するもの。

通常Errorでは、該当入力を破棄・再取得することで通信を継続できる場合がある。

代表例：

* 単発Frame CRC不一致
* 構文解析不能なQR
* 不正Payload Length
* 不正Padding
* 未定義Data Type
* First QRとして必要な情報の不整合
* String復元失敗

---

## 84.4 Critical Error

通信そのものを継続できないもの。

代表例：

* First QRの通信確立不能
* CRC連続エラー閾値到達
* 全Frame取得後のOverall CRC不一致
* その他プロトコル上継続不能な状態

Critical Error発生時には通信を停止し、現在の通信状態・Frame保持状態等を破棄する。

次回Startでは新通信としてFrame 0 / Waiting for Firstから開始する。

---
