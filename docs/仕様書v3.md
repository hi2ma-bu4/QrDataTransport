# QrDataTransport 仕様書 v3

## 1. 概要

**QrDataTransport** は、Webブラウザ間でカメラとQRコードを利用してデータ通信を行うライブラリである。

送信側ブラウザでQRコードを高速に切り替えて表示し、受信側ブラウザがカメラを使用して連続的にQRコードを読み取ることで、複数のQRコードに分割されたデータを転送する。

実装言語は以下を使用する。

- TypeScript
- Rust / WebAssembly

通信自体は一方向とするが、ライブラリ自体は送信・受信の双方に対応する。

---

# 2. 基本方針

QrDataTransportは、以下の3層に分離する。

```text
┌─────────────────────────────────────┐
│ Browser Runtime API                 │
│                                     │
│ Camera / DOM / Canvas / Worker      │
│ MediaStream / Timing                │
└─────────────────┬───────────────────┘
                  │
                  ▼
┌─────────────────────────────────────┐
│ Transport API                       │
│                                     │
│ 通信制御・フレーム送受信              │
└─────────────────┬───────────────────┘
                  │
                  ▼
┌─────────────────────────────────────┐
│ Data API                            │
│                                     │
│ Uint8Array / QR Data / Protocol     │
│ Frame / Checksum / Reconstruction   │
└─────────────────────────────────────┘
```

各層の責務を明確に分離し、QRデータ処理とブラウザ固有処理が直接依存しない構造とする。

---

# 3. API構成

公開APIは以下の3つを基本とする。

1. Data API
2. Transport API
3. Browser Runtime API

---

# 4. Data API

## 4.1 目的

通信するデータおよびQR通信データを扱う低レイヤーAPI。

ブラウザ、DOM、Camera、Canvas等のブラウザ実行環境には依存しない。

内部の基本データ形式は `Uint8Array` とする。

---

## 4.2 主な責務

- `Uint8Array` の受け取り
- データ分割
- フレーム生成
- フレーム番号管理
- QR用通信データ生成
- QR通信データ解析
- フレーム再構成
- フレームChecksum
- 全体Checksum
- データフォーマット管理
- 通信終了情報の処理

---

## 4.3 データフロー

### 送信

```text
Input Data
    ↓
Data Format
    ↓
Protocol Encode
    ↓
Frame Split
    ↓
QR Data
```

### 受信

```text
QR Data
    ↓
Protocol Decode
    ↓
Frame Validation
    ↓
Frame Reconstruction
    ↓
Overall Checksum Validation
    ↓
Uint8Array
```

---

# 5. 入力データ形式

内部形式は `Uint8Array` とする。

High-level APIでは複数の入力形式を使用できる構造とする。

現時点で通信プロトコル上定義するデータタイプは以下。

| Mode | データタイプ |
|---|---|
| `0b00` | `Uint8Array` |
| `0b01` | UTF-8 String |

2bit中、現時点では `0b10` および `0b11` は未使用とする。

将来的にデータタイプを追加する場合は、ライブラリフォーマットバージョンとの互換性を考慮する。

---

# 6. QR通信プロトコル

## 6.1 基本構造

通信データは複数のQRフレームへ分割する。

QRは以下の3種類の構造を持つ。

1. 先頭QR
2. 中間QR
3. 最終QR

```text
┌──────────────┐
│ 1QR目        │
│ Start = 1    │
│ 全QR枚数     │
│ Frame Number │
│ Data Type    │
│ Payload      │
│ Checksum     │
└──────────────┘
        ↓
┌──────────────┐
│ 2～N-1 QR目  │
│ Start = 0    │
│ Frame Number │
│ Payload      │
│ Checksum     │
└──────────────┘
        ↓
┌──────────────┐
│ 最終QR        │
│ Start = 0    │
│ Frame Number │
│ Payload      │
│ Checksum     │
│ Overall CRC  │
└──────────────┘
```

1QR目・中間QR・最終QRでヘッダー構造を変えることで、共通のフレーム順序を使用する。

---

# 7. QRフレームのビット構造

## 7.1 先頭QR

先頭QRは以下の順序で格納する。

```text
[Start Bit]
[Library Format Version]
[Total QR Count]
[Frame Number]
[Data Type]
[Payload Length]
[Payload]
[Checksum]
```

各フィールドの仕様：

| フィールド | サイズ |
|---|---:|
| Start Bit | 1bit |
| Library Format Version | 4bit |
| Total QR Count | 16bit |
| Frame Number | 可変 1～16bit |
| Data Type | 2bit |
| Payload Length | 可変 |
| Payload | Payload Lengthに依存 |
| Checksum | 16bit |

---

## 7.2 中間QR

中間QRは以下の順序で格納する。

```text
[Start Bit]
[Frame Number]
[Payload Length]
[Payload]
[Checksum]
```

各フィールドの仕様：

| フィールド | サイズ |
|---|---:|
| Start Bit | 1bit |
| Frame Number | 可変 1～16bit |
| Payload Length | 可変 |
| Payload | Payload Lengthに依存 |
| Checksum | 16bit |

---

## 7.3 最終QR

最終QRは以下の順序で格納する。

```text
[Start Bit]
[Frame Number]
[Payload Length]
[Payload]
[Checksum]
[Overall Checksum]
```

各フィールドの仕様：

| フィールド | サイズ |
|---|---:|
| Start Bit | 1bit |
| Frame Number | 可変 1～16bit |
| Payload Length | 可変 |
| Payload | Payload Lengthに依存 |
| Checksum | 16bit |
| Overall Checksum | 32bit |

---

# 8. Start Bit

QRデータの先頭1bitをStart Bitとする。

| QR | Start Bit |
|---|---:|
| 先頭QR | `1` |
| 中間QR | `0` |
| 最終QR | `0` |

先頭QRのみ `1` とすることで、通信開始前のQRを識別できる。

---

# 9. Library Format Version

ライブラリフォーマットバージョンは4bitとする。

使用可能なバージョンは、

```text
0b0001 ～ 0b1111
```

とする。

`0b0000` は使用しない。

初期バージョンは、

```text
0b0001
```

から開始する。

このバージョンはQRデータのプロトコルフォーマットを識別するためのものであり、ライブラリのnpmパッケージバージョン等とは別物とする。

---

# 10. Total QR Count

先頭QRにのみ、全QR枚数を含める。

サイズは16bit。

```text
最大値 = 65535
```

したがって、1回の通信で使用できるQRは最大65535枚とする。

先頭QRを `1`、最終QRを `N` とした場合、

```text
Total QR Count = N
```

となる。

---

# 11. Frame Number

各QRにはフレームナンバーを付与する。

フレームナンバーは、

```text
1 ～ Total QR Count
```

を使用する。

フレームナンバーのビット数は、Total QR Countを表現するために必要な最小ビット数とする。

範囲：

```text
1～16bit
```

例：

```text
Total QR Count = 1
→ Frame Number = 1bit

Total QR Count = 2
→ Frame Number = 2bit

Total QR Count = 3
→ Frame Number = 2bit

...

Total QR Count = 65535
→ Frame Number = 16bit
```

具体的には、Total QR Count以上の値を表現可能となる最小ビット数を使用する。

---

# 12. Payload Length

Payload Lengthは可変長整数として格納する。

構造は、

```text
[6bit Data][1bit Continuation Flag]
```

とする。

1単位は7bit。

```text
┌───────────────┬──────────────┐
│ Data          │ Continuation │
│ 6bit          │ 1bit         │
└───────────────┴──────────────┘
```

Continuation Flagにより、次の7bit単位が存在するかを示す。

```text
Continuation = 0
→ この単位で終了

Continuation = 1
→ 次の7bit単位へ継続
```

Payload Lengthの最大値・実装上の上限は、QR Versionおよびその他のプロトコルフィールドによって決定される。

---

# 13. Payload

Payloadには実データを格納する。

内部データ形式は `Uint8Array` とする。

Payload LengthはPayloadのバイト長を表す。

QR VersionおよびError Correction Levelによって利用可能な容量が変化するため、実際のPayload容量はData APIが使用するQR設定から算出する。

---

# 14. Data Type

Data Typeは2bit。

現時点で以下を定義する。

```text
0b00 = Uint8Array
0b01 = UTF-8 String
0b10 = 未使用
0b11 = 未使用
```

High-level APIで入力されたデータは、最終的にData APIでこの形式へ変換する。

---

# 15. Frame Checksum

各QRフレームに16bitのChecksumを付加する。

アルゴリズム：

```text
CRC-16/CCITT-FALSE
```

Checksumは、そのQRに含まれるChecksum自身より前のビット全てを対象として計算する。

つまり、先頭QR・中間QR・最終QRのいずれも、

```text
[Checksumより前の全ビット]
        ↓
CRC-16/CCITT-FALSE
        ↓
16bit Checksum
```

となる。

最終QRのOverall ChecksumはFrame Checksumの計算対象には含めない。

---

# 16. Overall Checksum

最終QRにのみ、通信全体のChecksumを含める。

サイズ：

```text
32bit
```

アルゴリズム：

```text
CRC-32/ISO-HDLC
```

Overall Checksumの対象は、各QRのPayloadをパースした後、それらをフレーム順に結合した結果とする。

```text
Frame 1 Payload
        +
Frame 2 Payload
        +
...
        +
Frame N Payload
        ↓
Payload Concatenation
        ↓
CRC-32/ISO-HDLC
        ↓
Overall Checksum
```

つまり、QR上に格納されているヘッダー、Frame Number、Payload Length、Frame Checksum等はOverall Checksumの直接の対象ではない。

---

# 17. 通信順序

QRは、

```text
1 → 2 → 3 → ... → N
```

の順序で送信する。

送信後は、

```text
1 → 2 → ... → N → 1 → 2 → ... → N → ...
```

のように、1からNまでの順番を繰り返すループ方式とする。

これは送信側が受信側の状態を把握できないためである。

送信側は、

- 受信側が現在どのフレームを待っているか
- どのフレームまで受信したか
- カメラがQRを認識できているか

を基本的には知ることができない。

そのため、送信側から受信側へのACK等を前提とせず、一定の順序でQRを繰り返し表示する。

---

# 18. 通信開始

通信は先頭QRを読み込むまで開始しない。

先頭QRには、

- Library Format Version
- Total QR Count
- Frame Number
- Data Type
- Payload

等、後続QRを処理するために必要な情報が含まれるため、これを通信開始情報として利用する。

---

# 19. 先頭QR読み込み前のQR

先頭QRをまだ正常に読み込めていない状態で、先頭QR以外のQRを読み込んだ場合、そのQRは仮読み込みとして扱う。

この時点では内容をパースしない。

```text
QR受信
   ↓
先頭QRか？
   │
   ├─ Yes → 検証・通信開始
   │
   └─ No  → 生データとして保持
```

仮読み込みしたQRは保持しておき、先頭QRが正常に読み込まれた後に処理する。

---

# 20. 先頭QR読み込み後の処理

先頭QRを読み込み、Frame Checksum等の検証が成功した時点で通信を開始する。

その後、

1. 先頭QRから通信情報を取得
2. それまで保持していた仮読み込みQRを処理
3. 以降に読み込んだQRを順次処理

する。

```text
先頭QR
  ↓
検証
  ↓
通信情報確定
  ↓
仮読み込みQRをパース
  ↓
以降のQRをパース
```

仮読み込みデータについても、確定した通信情報に従って処理する。

---

# 21. 重複QR

Frame Numberによって重複QRを判定する。

既に正常に受信・保持済みのFrame Numberを再度受信した場合、そのQRは重複として扱い、データへ二重に追加しない。

```text
1 → 2 → 2 → 3
        ↑
      重複
```

Frame Numberを基準に重複を排除する。

---

# 22. 不足QR

必要なFrame Numberがまだ読み込まれていない場合、そのフレームが読み込まれるまで待機する。

例えば、

```text
1 → 2 → 4 → 5
```

となった場合、Frame 3が不足しているため、Frame 3が読み込まれるまで通信完了にはしない。

送信側は1～Nの順序をループするため、

```text
...
N → 1 → 2 → 3
```

と進んだ際に不足していたFrame 3を取得できる。

---

# 23. 通信完了

Total QR Countが `N` の場合、Frame Number `1～N` の全フレームが揃った状態を通信データ完成状態とする。

その後、PayloadをFrame Number順に結合する。

```text
Payload 1
   +
Payload 2
   +
...
   +
Payload N
   ↓
Complete Payload
```

最終的に最終QRから取得したOverall Checksumと比較する。

Overall Checksumが一致した場合に、データを正常な通信結果として返却する。

---

# 24. QR Version

QR Versionは利用者が設定可能とする。

指定可能な範囲：

```text
1 ～ 40
```

Error Correction Levelも利用者が指定可能とする。

```text
L
M
Q
H
```

デフォルト：

```text
QR Version = 5
Error Correction Level = M
```

---

# 25. QR Payload容量

1QRあたりの実際の使用可能バイト数は、以下によって決定される。

- QR Version
- Error Correction Level
- QRエンコードライブラリ
- QrDataTransportのプロトコルヘッダー
- Frame Number
- Payload Length
- Checksum
- その他のプロトコル情報

具体的な使用可能バイト数は、実際に使用するQRライブラリの仕様をもとにData API側で算出する。

QrDataTransportの仕様として、特定のQR Versionに対して固定のPayloadバイト数をハードコードすることは現時点では行わない。

# 26. Browser Runtime API

## 26.1 目的

ブラウザ固有の実動作を管理するAPI。

通信データや通信プロトコル自体には依存しない。

主に以下を担当する。

- Camera
- DOM
- Canvas
- Worker
- MediaStream
- QR表示
- カメラ映像取得
- フレーム取得タイミング
- ブラウザAPIとの接続

---

# 27. Browser Runtime APIとData APIの境界

送信側と受信側でRuntimeとData APIの責務を分ける。

## 27.1 送信側

送信側Runtimeは、**QRのmodule情報**を受け取る。

module情報は白黒の2値データとして扱う。

概念：

```text
[1, 1, 0, 0, ...]
```

このmodule情報から、Runtime側でQRを表示する。

QRデータ自体の生成はData API側で行う。

```text
Data
 ↓
Data API
 ↓
QR Data
 ↓
QR Module Data
 ↓
Browser Runtime API
 ↓
Canvas / DOM
 ↓
Display
```

QR Module Dataは、Worker上のData APIで生成できる構造とする。

---

## 27.2 受信側

受信側Runtimeは、カメラから取得した**画像**を返却する。

```text
Camera
 ↓
Browser Runtime API
 ↓
Image
 ↓
Data API
 ↓
WASM
 ↓
QR解析
 ↓
QR Data
```

受信側では、RuntimeがQRデータそのものを解析するのではなく、画像をData APIへ渡す。

---

# 28. 受信時のWASM処理

受信側では、

```text
Browser Runtime API
        ↓
Image
        ↓
同期側 Data API
        ↓
Worker
        ↓
Worker側 Data API
        ↓
Rust / WASM
        ↓
QR解析
        ↓
各QRのデータ
        ↓
TypeScriptでUint8Array結合
        ↓
結果返却
```

という構造を基本とする。

画像解析・QR解析の具体的な処理範囲は、Rust/WASMの性能調査後に決定する。

---

# 29. Worker

可能な環境ではWorkerを利用する。

Workerが利用できない場合、または設定で無効化されている場合はMain Threadへフォールバックする。

Worker使用時と非使用時で処理ロジックを二重実装しない。

```text
             Common Processing
                    │
             Runtime Wrapper
              /           \
             /             \
    Main Runtime       Worker Runtime
          │                   │
          ▼                   ▼
    Main Thread             Worker
```

---

# 30. Workerの役割

Workerは、特にData API側の処理および高負荷なQR処理に利用する。

送信側では、Data APIによるQRデータ生成・module情報生成をWorker上で行えるようにする。

受信側では、Runtimeから渡された画像をWorker側Data APIへ送り、WASMによる画像解析・QR解析を行える構造とする。

---

# 31. Workerの提供方式

利用者がWorker用JavaScriptファイルを別途指定する必要がない構成を目標とする。

同一JavaScriptファイルから自身をWorkerとして起動できる構造とする。

概念：

```ts
if (isWorkerContext()) {
    runWorker();
} else {
    runMain();
}
```

具体的なWorker生成方式は未決定。

候補：

- Module Worker
- Blob Worker
- その他

CSP、ESM、CDN等との互換性については実装時に検討する。

---

# 32. DOM関連API

Browser Runtime APIでは、DOMを利用した実動作を利用者が制御できるAPIを提供する。

特に、通信の開始・終了をユーザー側から指定できるようにする。

想定する操作：

- 通信開始
- 通信終了
- Camera開始
- Camera停止
- QR表示開始
- QR表示停止
- Runtime状態取得

具体的なメソッド名は未決定。

# 33. Canvas設定

送信側のQR表示に使用するCanvasについて、利用者が指定できるAPIを提供する。

Canvasは以下の指定方法を検討する。

- Canvas element自体を指定
- Canvas elementのIDを指定
- ライブラリ側でCanvasを生成

例：

```ts
{
    canvas: HTMLCanvasElement
}
```

または、

```ts
{
    canvasId: "qr-canvas"
}
```

具体的なAPIは未決定。

---

# 34. Canvasサイズ

Canvasサイズはライブラリ設定から指定可能とする。

ただし、基本設定ではCanvasサイズを明示的に指定しない。

未指定の場合は自動リサイズを行う。

QR自体のmoduleサイズは通信中に変更しないため、QRサイズの変更は基本的に初回のみ行う。

概念：

```text
初期化
 ↓
Canvasサイズ決定
 ↓
QRサイズ決定
 ↓
通信中は固定
```

具体的な自動リサイズ条件およびサイズ算出方法は未決定。

---

# 35. 通信速度設定

QR切り替え速度は固定値としない。

利用者が設定によって変更できる構造とする。

設定対象の候補：

- QR表示FPS
- QR切り替え間隔
- 同一QRの表示回数
- QR解析頻度
- カメラFPS
- QR Version
- Error Correction Level
- QRサイズ
- Worker使用
- その他パフォーマンス関連設定

ただし、通信順序自体は常に、

```text
1 → 2 → ... → N
```

とする。

---

# 36. Data APIとRuntime APIの責務境界

重要な設計原則として、以下を分離する。

```text
「何を送るか」
        ↓
Data API

「通信をどう進行させるか」
        ↓
Transport API

「ブラウザ上でどう動かすか」
        ↓
Browser Runtime API
```

特に以下を混在させない。

```text
QRデータ生成
    ≠
QR表示

QRデータ解析
    ≠
Camera制御

通信プロトコル
    ≠
Worker制御

データ再構成
    ≠
DOM操作
```

---

# 37. Rust / WebAssembly

Rust / WASMは、高負荷な画像処理・QR解析等への利用を想定する。

ただし、Rust/WASMへどこまで処理を移すかは現時点では完全には確定していない。

以下について調査・実測する。

- 画像解析
- QR検出
- QRデコード
- SIMD
- WebAssembly性能
- WASMへの画像データ転送コスト
- メモリコピーコスト
- Canvasとの連携
- OffscreenCanvasとの連携
- Workerとの組み合わせ

現時点での基本構造は、

```text
Browser Runtime
      ↓
Image
      ↓
Data API
      ↓
Rust / WASM
      ↓
QR Data
```

とする。

# 45. v3で確定した設計原則

1. ライブラリ名は `QrDataTransport` とする。
2. 通信自体は一方向とする。
3. ライブラリは送信・受信の双方を実装する。
4. 内部データ形式は `Uint8Array` とする。
5. High-level APIでは複数の入力データ形式を利用可能にする。
6. 通信データ内にData Typeを含める。
7. 現時点のData Typeは `Uint8Array` とUTF-8 Stringとする。
8. QR 1枚を1フレームとして扱う。
9. 先頭QR・中間QR・最終QRでデータ構造を分ける。
10. 先頭QRのStart Bitは`1`、それ以外は`0`とする。
11. Library Format Versionは4bitとし、`0b0`を使用せず`0b1`から開始する。
12. Total QR Countは16bit、最大65535枚とする。
13. Frame NumberはTotal QR Countを表現できる最小ビット数を使用する。
14. Frame Numberは1～16bitとする。
15. Payload Lengthは6bit Data + 1bit Continuation Flagの可変長形式とする。
16. Frame Checksumは16bitのCRC-16/CCITT-FALSEとする。
17. Frame ChecksumはChecksumより前の全ビットを対象とする。
18. Overall Checksumは32bitのCRC-32/ISO-HDLCとする。
19. Overall Checksumはパース後の全Payload結合結果を対象とする。
20. QRは`1 → 2 → ... → N`の順で送信する。
21. 送信側は受信側の状態を把握できないため、1～Nの順序をループする。
22. 先頭QRを正常に読み込むまで通信を開始しない。
23. 先頭QR前に受信したQRは仮読み込みとして保持し、先頭QR確定後にパースする。
24. Frame Numberによって重複QRを排除する。
25. 不足Frameは該当Frameが読み込まれるまで待機する。
26. 全Frame取得後にPayloadをFrame Number順に結合する。
27. 最終的にOverall Checksumを検証して通信結果を確定する。
28. QR Versionは1～40で指定可能とする。
29. Error Correction LevelはL/M/Q/Hから指定可能とする。
30. デフォルトQR Versionは5とする。
31. デフォルトError Correction LevelはMとする。
32. 1QRあたりの実効Payload容量は実際に使用するQRライブラリから算出する。
33. 公開APIをData API、Transport API、Browser Runtime APIの3層に分離する。
34. Data APIはブラウザ固有APIへ依存しない。
35. Transport APIはData APIとBrowser Runtime APIを接続する。
36. Browser Runtime APIはCamera、DOM、Canvas、Worker等を管理する。
37. 送信側RuntimeはQR Moduleの白黒2値データを受け取る。
38. 送信側のQRデータ生成はData API側で行う。
39. 受信側Runtimeはカメラから取得したImageを返却する。
40. 受信側のImageはData APIからWorker側のData API / WASMへ渡す。
41. QR解析後の各QRデータはTypeScript側で`Uint8Array`として結合する。
42. Worker / OffscreenCanvasが利用可能な場合は利用できる構造とする。
43. Workerが利用できない場合、または設定で無効化された場合はMain Threadへフォールバックする。
44. Worker使用時と非使用時で共通処理を二重実装しない。
45. Workerは同一JavaScriptファイルから起動できる構造を目標とする。
46. DOM関連APIから通信の開始・終了をユーザーが指定できるようにする。
47. DOM関連APIからCanvas自体またはCanvas IDを指定できるようにする。
48. Canvasサイズは設定可能とする。
49. Canvasサイズ未指定時は自動リサイズを基本とする。
50. QRサイズは固定とし、基本的に初回のみ変更する。
51. 速度・QRサイズ等の主要パラメータは設定可能とする。
52. Rust/WASMの担当範囲は性能調査結果をもとに最終決定する。
53. 将来的な双方向通信への拡張を妨げない設計とする。
